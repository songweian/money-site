2026 年 11 月 4 日下午（UTC），月之暗面把 Kimi K3.1 Pro 的全量权重放到了 Hugging Face，仓库地址是 [moonshotai/Kimi-K3.1-Pro](https://huggingface.co/moonshotai/Kimi-K3.1-Pro)，公开且没有申请门槛。这和它在技术博客里写下的期限对得上：产品和 API 先上线，完整权重在 2026 年 11 月 4 日之前放出。

对中小团队，值得动手的不是「又一个最大的模型」，而是四件已经能核对的事：权重大约 1.56 TB，自建要多卡；API 今天就能按官方单价试；许可证允许使用、修改、微调和再分发，但卖模型服务和超大产品各有一条门槛；更快的 Highspeed 在 API 里有独立模型 ID，公开仓库列表里没有第二份权重。模型按任务分工的总原则，仍是 [按任务分工，不要整站换新](/posts/october-ai-model-roles/)。

## 模型卡上能核对的规格

下面全部来自该仓库的模型卡，本文没有改单位。

| 模型卡字段 | 模型卡写法 |
| --- | --- |
| 架构 | 混合专家（MoE） |
| 总参数 / 每 token 激活 | 2.8T / 104B |
| 层数 | 93；其中 69 层 KDA，24 层 Gated DSA |
| 稠密层 | 1。卡片没有说明这 1 层是含在 93 里还是另计 |
| 专家 | 896 个，每 token 选 16 个，另有 2 个共享专家 |
| 上下文 | 1,048,576 token |
| 模态 | 文本、图像 |
| 视觉编码器 | MoonViT-V2，401M 参数 |
| 量化 | MXFP4 权重 / MXFP8 激活，量化感知训练 |
| 相对 K3 的结构变化 | 全注意力的 Gated MLA 换成 Gated DeepSeek Sparse Attention，为了更省的长上下文 |

2.8T 是参数库存。模型卡写每个 token 激活 104B，并在 896 个专家里选 16 个。账单和显存都不要按「每个 token 把 2.8 万亿参数全部算一遍」来报。

上下文以 1,048,576 为准。技术博客和 vLLM 博客口语里的「1M / 100 万」是同一量级的说法。定价页对全部 K3 系列写的也是 1,048,576。单次请求实际能带多少，还受你设置的输出长度和历史思考占用的限制，见下文试跑。

模态栏是文本和图像。技术博客里的三维例子，写的是模型写脚本去驱动 Blender、CAD 一类工具，以及 kimi.ai 上的 3D Make。本文不把「能看图」写成「API 会返回一张改好的图」。

量化是训练时就做的。模型卡写权重 MXFP4、激活 MXFP8，并注明 quantization-aware training。ArtificialWatch 据此把它理解成月之暗面自己服务时使用的精度，而不是事后再压一次的包。本文沿用这个限定：仓库里这份就是模型卡写的服务精度。

文件体积用两个来源一起写，避免把「大约」说成精确到字节的分片之和：

- Hugging Face 模型 API 的 `usedStorage` 是 1,561,355,732,732 字节，按 1 TB = 10^12 字节计为 1.561 TB。这是整个仓库的占用。本文读取该字段的时间是 2026-11-05（北京时间）。`gated` 为 false。
- `siblings` 里 safetensors 共 96 个，文件名从 `model-00001-of-000096.safetensors` 到 `model-00096-of-000096.safetensors`。
- ArtificialWatch 同日把这 96 个分片写成合计 1.56 TB，并写这和 Kimi K3 发布时的体积相同。

1.56 TB 是下载和磁盘的量级。它不包含推理时的 KV 缓存。上下文拉到接近 1,048,576 时，缓存还会再占一截，vLLM 的博客把这一截按格式和并行方式分开测过，那是他们的机器，不是你的报价单。

65.7 和 64.4 用来挑选试跑样本：一小段你确实要改的代码，一份要核对数字的财务或行政材料。它们不能写成你的合并率或报表准确率。幻觉那一行尤其不要外推。博客自己已经把样本说成「故意挑模型容易错的情况」。

技术博客还用内部基准 xdev-bench-hard 说明网络安全相关数据删减之后的结果：未做删减的检查点是 90.5%（pass@3），最终放出的 K3.1 Pro 是 81.0%。博客称，开放权重的进攻性能力仍落后于已经公开至少三个月的前沿闭源模型。这是厂商自述。它不能换成对生产系统做未授权测试，也不能当成你仓库的漏洞发现率。办公试跑仍然不要放入客户合同、未公开经营数字、账号和密钥。

## 官方 API 单价，以 2026-11-05 打开的定价页为准

单价来自 [Model Inference Pricing](https://platform.kimi.ai/docs/pricing/chat)。本文于 2026-11-05（北京时间，对应 2026-11-04 晚间 UTC）打开该页。页面内嵌的 `lastModified` 是 `2026-10-30T12:09:57.621Z`。1 MTok = 1,000,000 token。价格不含税。

| 模型 ID | 未命中输入 | 输出 | 缓存命中 | 5 分钟写入 | 1 小时写入 |
| --- | --- | --- | --- | --- | --- |
| `kimi-k3.1-pro` | 2.00 美元 | 10.00 美元 | 0.20 美元 | 2.00 美元 | 4.00 美元 |
| `kimi-k3.1-pro-highspeed` | 4.00 美元 | 20.00 美元 | 0.20 美元 | 4.00 美元 | 8.00 美元 |
| `kimi-k3` | 3.00 美元 | 15.00 美元 | 0.30 美元 | 3.00 美元 | 6.00 美元 |

三行都是每百万 token。K3 那一行放在这里，是因为定价页同一张表就有它，方便看「换到 3.1 Pro 时单价是升是降」。K3 的输入 3 美元、输出 15 美元，K3.1 Pro 是 2 美元和 10 美元。Highspeed 的输入和输出是标准 Pro 的 2 倍，缓存命中仍是 0.20 美元。速度上的「2 到 3 倍」是技术博客的说法，和这张价格表不是同一个倍数，不要把 2 倍单价理解成 2 倍速度的标价。

分项怎么读，以 [上下文缓存指南](https://platform.kimi.ai/docs/guide/context-caching) 为准。该页用 `kimi-k3` 举例：未命中的部分按次按输入价计；前缀第一次写入按写入价计一次；命中的部分按次按缓存价计，命中不再另收写入费，并按原来的 TTL 免费续期。定价页写，K3 系列默认自动开启缓存，默认 TTL 5 分钟。缓存指南写，不足一整块的前缀写不进去，仍按未命中计。块有多大，该页没有给数字。

因此，`kimi-k3.1-pro` 的 5 分钟写入价和未命中输入价相同，都是 2 美元。第一次把前缀写进默认缓存，输入侧金额和「全部按未命中计」相同。节省出现在随后的命中：同一段从 2 美元降到 0.20 美元。1 小时写入是 4 美元，高于未命中输入。复用间隔会超过 5 分钟、又希望留下缓存时，才值得把 TTL 改成 1 小时。若账单把同一段 token 既算未命中又算写入，以账单为准。

[Batch 定价页](https://platform.kimi.ai/docs/pricing/batch) 写：`kimi-k3.1-pro` 和 `kimi-k3` 的 Batch 按标准价的 60% 计，面向不需要实时返回的大批量任务。同一页的模型列表里有 `kimi-k3.1-pro`、`kimi-k3`、`kimi-k2.7-code`、`kimi-k2.6`，没有把 `kimi-k3.1-pro-highspeed` 写进 Batch。本文不假设 Highspeed 享受这 60%。该页还写：K3.1 Pro 和 K3 的 Batch 仍收取 Cache Write；因为异步并发，缓存命中是尽力而为，不保证。

思考 token 会计进用量。[思考模型说明](https://platform.kimi.ai/docs/guide/use-thinking-models) 写：`kimi-k3.1-pro` 的推理和 Preserved Thinking 始终打开，不能靠关掉思考来省 token；`reasoning_effort` 可以设 `low`、`high`、`max`，默认 `max`。`reasoning_content` 计入 token 消耗。多轮要把历史思考原样带回，这些内容继续占上下文并计费。定价页没有按三档各标一个单价。默认 max 时，屏幕上很短的回答仍可能对应很长的输出账单。

## 按官方单价算的一笔试跑账

公式按「每百万 token」写。100 万 token 才是 1。下面的条数是**示例假设**，用来演示乘法，不是月之暗面的统计，也不是你的账单。

未命中、不走缓存时：

费用 = 未命中输入 × 输入单价 + 输出 × 输出单价

取一笔和办公试跑差不多的用量：20 万未命中输入（0.2）加 5 万输出（0.05）。

| 模型 | 算式 | 金额 |
| --- | --- | --- |
| `kimi-k3.1-pro` | 0.2×2 + 0.05×10 | 0.90 美元 |
| `kimi-k3.1-pro-highspeed` | 0.2×4 + 0.05×20 | 1.80 美元 |
| `kimi-k3` | 0.2×3 + 0.05×15 | 1.35 美元 |

同一笔若是 18 万缓存命中、2 万未命中、5 万输出，标准 Pro 为 0.18×0.20 + 0.02×2 + 0.05×10 = 0.576 美元。第一次把这 18 万按默认 5 分钟写入、再加上 2 万未命中和 5 万输出，是 0.18×2 + 0.02×2 + 0.05×10 = 0.90 美元，和全部未命中相同。改成 1 小时写入的第一次，是 0.18×4 + 0.02×2 + 0.05×10 = 1.26 美元。

这 0.90 美元只在「输出 5 万 token」时成立。若默认 max 把这一次的输出记到 15 万 token（仍是示例假设，官方没有公布档位倍数），输出费用为 0.15×10 = 1.50 美元，加上输入 0.40 美元，合计 1.90 美元。先看控制台里的 `usage`，再决定要不要把 `reasoning_effort` 从 max 降到 high 或 low。

Batch 按标准价 60% 理解时，上面 0.90 美元乘 0.6 等于 0.54 美元。这是本文的乘法，定价页没有另行打印一行「Batch 单价 = 1.20 / 6.00」。Cache Write 若在 Batch 里另计，0.54 美元就偏低。缓存命中不保证，不要把 0.576 美元写进 Batch 预算。

试跑周可以先封顶：标准 Pro、全部未命中的这种回合最多 20 次，即 18.00 美元。命中上表那种缓存比例，20 次是 11.52 美元。超过就停，回头看人是否采纳，而不是把额度用满。常驻预算按未命中加默认 max 可能拉长的输出来报，缓存节省只在你量过重复前缀之后再扣。

本站 11 月 4 日的 [Hy4 文](/posts/tencent-hy4-workbuddy-guide/) 用过同一笔「20 万未命中输入 + 5 万输出」，按当时核对的 TokenHub 五折是 1.05 元人民币。这里的 0.90 美元是另一家、另一种货币。不要换算之后比谁更聪明。把一笔自己的用量放进一周预算的算法，和 [LongCat-2.5 的限时价](/posts/meituan-longcat-2-5-guide/) 是同一张表：先乘你的 token，再决定哪一段值得换。

## 这周怎么试：API 和 Kimi Code

默认模型先不动。K3.1 Pro 适合加进对比表的新列。一次只换一类任务。做法和分工那篇相同。

值得先试的，是你这周本来就要做、一天内能由人判断对错的活：一小段确实打算改的代码；一份要回原文核对金额、日期、负责人的长文档；一张你有权使用的图表。先不要交给它的：付款、对外发送、改权限，以及把整仓整月文档一次塞进 1,048,576 的上下文再看账单。

步骤可以收成七条：

1. 在 [platform.kimi.ai](https://platform.kimi.ai) 建密钥。模型 ID 用 `kimi-k3.1-pro`。思考模型文档里的示例基地址是 `https://api.moonshot.ai/v1`，走 OpenAI Chat Completions。模型卡写 API 同时提供 OpenAI 和 Anthropic 兼容。密钥放在环境变量里，不写进仓库。
2. 先不要改 `reasoning_effort`，用默认的 max 打通一次。然后把同一份材料再跑 `high` 和 `low`。只记三件事：人是否采纳、返工几分钟、这次 `usage` 里的输入和输出。官方没有公布三档相差多少 token。
3. 多轮和工具调用时，把 API 返回的整段 assistant 消息原样放回 `messages`，包括 `reasoning_content` 和 `tool_calls`。模型卡和思考模型文档都写了这一条。只回传可见的 `content`，下一轮会丢掉它刚才的思考。
4. 从上周的真实工作里抽三份，去掉客户姓名、未公开报价、账号和密钥。一份代码，一份长文档里的三个可核对问题，一份绝不能直接发出的邮件或报价。第三份两个模型都只出草稿，用来确认新模型没有被接到自动发送上。
5. 记录表固定六列：日期、任务、模型名、人是否采纳、返工分钟、账单金额。一周结束只留一个变化。两个一起换，就分不清差别来自哪里。
6. 交互太慢，再试 `kimi-k3.1-pro-highspeed`。输入 4 美元、输出 20 美元。用同一份材料比返工时间和账单，不比博客里的「2 到 3 倍」。
7. 不需要马上返回的分类、抽取，再考虑 Batch。模型 ID 仍用 `kimi-k3.1-pro`，并按上一节把 60% 理解成折扣说明，而不是一张已经印好的单价。

编程入口按技术博客：运行 Kimi Code，用 `/model` 选择 Kimi K3.1 Pro。Kimi Work 的版本要求写的是桌面端 3.1.0 或更新，Windows 和 Apple 芯片 Mac。企业管理员可以给组织打开 K3.1 Pro，博客写上线时默认关闭。本文没有登录企业控制台复核今天的开关，以你屏幕上的开关为准。

数据边界单独问。[零数据保留说明](https://platform.kimi.ai/docs/guide/zero-data-retention) 写：开放平台默认不把企业客户数据用于训练；ZDR 要企业客户另外申请，打开后请求内容在生成响应期间处理，返回后删除，法律要求保留的除外。Batch 不支持 ZDR。直接通过文件上传接口提交的图片和视频，该页写不能保证 ZDR。这是 API 平台的条款，不能自动套到 Kimi 网页或 App 的会员对话上。会员产品的保留期限，本文没有逐条核对。额度和训练用途要分成两列问，问法和 [挑免费额度](/posts/free-ai-tool-limits/) 相同。屏幕上没有数据使用说明时，客户材料不进入试跑。

## 什么情况下先不要自建

自建要同时说得清三件事：数据必须留在你指定的环境里，或者你必须在不依赖官方 API 的前提下做定制；你已经有下面某一档机器，或者云厂商按那一档给你的报价你算得过；你做完下一节的许可检查。三句缺一句，就继续用 `kimi-k3.1-pro`。

模型卡推荐的引擎是 vLLM、SGLang、TokenSpeed。本文读过的部署说明是 [vLLM 2026-11-04 的首日支持](https://vllm.ai/blog/2026-11-04-kimi-k31-pro)。SGLang 和 TokenSpeed 的命令以模型卡上的链接为准，本文没有另跑。

vLLM 写它在首日支持 NVIDIA GPU、AMD GPU、Google TPU 和阿里巴巴平头哥振武 PPU。快速开始里的 NVIDIA 和 AMD 示例都带 `--tensor-parallel-size 8`，模型名是 `moonshotai/Kimi-K3.1-Pro`。这是示例参数，不是「最少 8 张卡」的承诺，也没有写成一张消费级显卡就能装下 1.56 TB。

同一篇里写出的验证配置还有：

- TPU：通过 vllm-torchtpu，在 16 芯片的 TPU v7x 切片上验证，布局是 TP32 加 EP32。
- 振武 810E：两节点，TP32 / EP32。
- 振武 M890：四节点，TP8 / DP4 / EP32。

博客里的速度，例如 GB300 上 AgentX 延迟敏感端最高 375.9 token/秒/用户、Rubin 上 815.6 token/秒/用户，是 vLLM 自己的测量。用来了解「他们在哪一档机器上跑通了」，不用来写你的服务水平协议。KV 能装下多少个 100 万 token 上下文，博客按 FP8、NVFP4 和是否做解码上下文并行分开给了 GB300 上的数字。那些数字随格式变化，本文不摘成一句「8 张卡就能同时挂住几个满上下文」。

因此，这周先不要自建的情况可以写成四句。只想知道回答好不好。手头没有多卡或多节点的现成机器。目标是 Highspeed 的响应速度，而公开仓库里没有那份权重。调用量还停在上一节那种每周几十美元以下的试跑。数据不能出门、机器也已经在机房里时，再把 vLLM 的示例命令交给负责推理的人，并单独做许可检查。固定成本（电费、折旧、云主机月租）模型卡和这篇 vLLM 博客都没有按你的机房报价，本文不算这笔。

这个顺序和本站写过的 [Mistral Large 4 开放权重](/posts/mistral-large-4-open-weight-guide/) 相同：先用 API 把质量测完，机器档对不上就不要采购。两家的单价、上下文和许可证条文各自独立，不要把 Large 4 的美元价套到 Kimi 上。

1. 版权声明和许可声明要留在副本或实质部分里。使用要符合适用法律。
2. 「模型即服务」指把语言模型的推理或微调提供给第三方（例如 API），并且对方能对输入、参数或训练数据施加实质性控制。许可证明确排除两类：能力只嵌在具体功能或工具链里的终端产品；仅仅把请求转到别人托管的模型。
3. 若被许可方或其关联方经营模型即服务，且任意连续 12 个月的合计收入超过 2000 万美元（或其他货币的等值），则在把本软件或其衍生作品用于任何商业目的之前，要和月之暗面另签协议。
4. 若软件或其衍生作品被用于月活超过 1 亿、或月收入超过 2000 万美元的商业产品或服务，用户界面要显著展示 `Kimi K3.1-Pro` 这串名字。大小写和连字符按许可证原文。
5. 第 2 条和第 3 条不适用于：内部使用，也就是不把软件、它的输出或底层能力提供给第三方；以及通过月之暗面官方产品或认证推理伙伴使用。认证伙伴的名单，这份 LICENSE 里没有列出。要确认某一家云厂商算不算，问 license@moonshot.ai。

小团队可以先对号入座。员工在自己的电脑上用官方 API 或 Kimi Code 写内部文档，走的是官方产品，第 2、3 条不适用。把权重放在公司内网、只给员工用、不对外提供接口，许可证把这定义为内部使用，同样不适用那两条。把模型嵌进一个具体功能、用户不能把它当成通用对话接口，许可证不把这种情况算作模型即服务；若这个产品本身已经超过月活或月收入门槛，第 4 条的署名仍然要单独看。对外出售推理 API，并且公司已经跨过 2000 万美元的 12 个月收入线，在商用前要另签。收入还没到线，不表示没有其他条款：版权声明、合法使用和「现状」条款仍然在。

## 常见问题

### 现在就能下载 Kimi K3.1 Pro 的权重吗？

能。`moonshotai/Kimi-K3.1-Pro` 公开且未设门槛。96 个 safetensors，仓库 `usedStorage` 约 1.56 TB。Highspeed 的 API 模型 ID 是 `kimi-k3.1-pro-highspeed`。公开模型列表里本文只看到标准 Pro 这一份仓库，ArtificialWatch 也没有确认到单独检查点。

### 小团队这周要不要买机器自建？

先不要。约 1.56 TB 的权重，加上 vLLM 示例里的 8 卡张量并行，以及 TPU、振武的多芯片或多节点验证配置，都超出「加一张游戏显卡」的范围。没有现成机器，用 API 或 Kimi Code 测质量。

### 把权重嵌进自己的产品，要不要另签协议？

先看用法和收入，并阅读 LICENSE。内部使用和官方产品、认证伙伴路径，第 2、3 条不适用。模型即服务且任意连续 12 个月收入超过 2000 万美元，商用前要另签。月活过 1 亿或月收入过 2000 万美元的产品要显著展示 `Kimi K3.1-Pro`。拿不准问 license@moonshot.ai。本文不是法律意见。

### 文中的 2 美元和 10 美元以后还准吗？

不保证。它们是 2026-11-05（北京时间）定价页上 `kimi-k3.1-pro` 的未命中输入和输出，每百万 token。页面 lastModified 显示 2026-10-30。改预算前再打开 [定价页](https://platform.kimi.ai/docs/pricing/chat)。文中的调用次数和 token 条数是示例假设。
