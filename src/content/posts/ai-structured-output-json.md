把模型输出接进程序时，最容易翻车的不是它不会写，而是它写得太「会」了——前面加一句「好的，这是你要的结果」，后面补一段「如果还需要调整请告诉我」，中间才是那串 JSON。人在界面里复制一下还能用，一旦进了自动化流水线，这点人味每次都是一次解析失败。

结构化输出不是一个提示词技巧，而是一整套工程约束：**先写清楚契约，再在解析层兜底，最后把失败变成可恢复的重试**。三件事缺一件，链路就稳不下来。

## 为什么「请返回 JSON」总是时灵时不灵

问题不在模型不听话，而在你要的东西和它被训练的目标，方向天生相反。

模型被优化成「生成一段对用户有帮助的回答」，帮助的很大一部分来自语气、铺垫和解释。而你真正要的是「生成一段能被机器直接解析的数据」。这两件事在自然语言里是冲突的：人味越足，机器越难读。

于是失败几乎总以这几种固定形态出现：

**客套话包裹**。输出前后各加一段自然语言，有的还带 emoji 或标题。
**代码围栏**。JSON 被包进 ```json 代码块里，外层还有一句说明。
**字段漂移**。字段名这次是 `name` 下次是 `title`；数字被写成 `"3"`；本该是数组的地方给了字符串；缺失值有时不出现、有时是 `null`、有时是 `"未知"`。
**长输出截断**。内容还没写完，输出就断了，右括号缺失，JSON 根本没法闭合。

前三种靠约束能解决，第四种要靠任务设计。把它们分开处理，是后面所有做法的前提。

## 三种约束强度：描述、契约、模式

同样是「让它输出结构化数据」，可以做到三种不同的强度，稳定性和代价也完全不同。

| 约束方式 | 具体做法 | 稳定程度 | 适用场景 | 代价 |
| --- | --- | --- | --- | --- |
| 描述式 | 在提示词里写「请用 JSON 格式返回」 | 低，经常夹带自然语言 | 一次性临时任务、人工会看结果 | 几乎为零，但不可靠 |
| 契约式 | 明确字段清单、类型、枚举、缺失值、禁止事项，并要求仅输出 JSON | 中高，偶发格式瑕疵 | 绝大多数自动化场景 | 需要多写两三百字约束 |
| 模式式 | 使用平台提供的 JSON 模式或函数调用能力，在解码阶段约束 | 高，语法层基本不会错 | 有平台能力可用、字段结构固定 | 依赖平台支持，字段需预先定义 |

三者的关系不是替代，而是叠加。即便平台支持模式式约束，也仍然建议保留一份文字契约——模式管的是「它用什么格式说话」，契约管的是「你要什么数据」。

要注意的是，各平台对结构化输出的支持方式、字段名和能力边界差异较大，且会随版本调整，是否能用、怎么用，以官方文档为准，不要在提示词里依赖某个你没验证过的行为。

## 写一份能落地的输出契约

契约不是越长越好，而是要把模型可能自由发挥的地方，一个一个堵死。一份能用的契约至少包含六个部分：

**任务目标**：一句话说清它要产出什么，写成可判定的形式，比如「判断这条客户反馈属于哪一类」，而不是「分析一下这条反馈」。

**字段清单**：逐字段写明名称、类型、含义，以及**缺失时该输出什么**。这一条最关键——不要让它自己决定没有数据时写什么，统一规定为 `null`，或者统一给一个枚举里的兜底值。

**枚举取值**：凡是分类、状态、标签类字段，都必须穷举所有允许的值，并额外准备一个 `unknown` 兜底。不穷举，它就会创造出你没准备过的新类别。

**禁止事项**：明确写出不要输出解释、不要加前后缀、不要使用代码围栏、不要输出契约之外的字段。负面约束的对齐效果往往比正面描述更好。

**一个正例**：给一个完整的、可以直接当作标准答案的示例。示例比描述管用得多。

**长度上限**：写明单次输出多少条、每条约多少字。这既是质量约束，也是截断保护。

还有两个容易忽略的细节：

一是**字段顺序按重要性排，长文本放最后**。输出被截断时，先被切掉的是末尾，把最关键的短字段放在前面，能保住大部分可用性。

二是**不要让它在数据之外先讲思路**。需要理由就设成契约里的一个字段，让解释待在 JSON 内部，而不是飘在外面。

## 校验层：解析失败不等于任务失败

拿到输出后不要直接 `parse`，先过三层。

**语法层**：能不能解析成合法 JSON。这一层的失败最廉价，也最值得自动修复——去掉首尾的代码围栏、截取第一个 `{` 到最后一个 `}` 之间的内容、清理尾逗号。这些都属于确定性修复，可以放心做。但要注意，只做机械修复，**不要猜测补半个括号**，猜错比失败更危险，因为它会产出看起来正常的脏数据。

**结构层**：字段是否齐全、类型是否正确、枚举值是否合法。这一层必须显式检查，因为语法合法不代表内容可用。缺字段时要能分辨：是输入里确实没有这个信息，还是模型漏了。

**语义层**：值本身合不合理。日期是否是合法日期、百分比是否在 0 到 100 之间、数量是否和条目数对得上。这层检查最容易被跳过，也最容易让脏数据一路流进数据库。

无论哪一层失败，都要保留原始输出再报错。坏样本是改进契约最直接的素材，丢掉它，下次还是会在同一个地方摔跤。

## 自动重试：把修正信号喂回去，而不是原样重跑

最常见的错误重试姿势，是把同一条提示词原样再发一次。这基本是在浪费额度：同样的输入、同样的采样范围，大概率会得到同样类型的错误。

有效的重试只有三种：

**带上失败原因重试**。把上一次的输出和具体的错误原因一起贴回去，让它针对这个问题修正。比如「上一次输出在 JSON 前加了一句说明，这次只输出 JSON，不要任何前缀」。这会显著提高一次成功率。

**降随机性重试**。如果问题是忽好忽坏而不是稳定出错，说明输出空间太自由，收紧随机性参数通常比改提示词更快见效。

**拆任务重试**。如果稳定死在长输出截断上，重试无用，必须改成多次短输出：先输出条数清单，再分批补全，每批处理有限条数。

重试还要有边界条件：设定最多重试次数、设定超时、设定成本上限，并且**必须准备兜底路径**。连续多次失败说明任务超出了单次输出能稳定承载的范围，此时应该拆任务、降目标，或者转人工，而不是继续加次数。

## 让结构化输出长期稳定的几条工程习惯

单次调通不难，难的是半年后它还稳。这几条习惯值得固化进流程：

**用固定测试集做回归**。准备二三十条覆盖正常、边界和刁难输入的用例，每次改契约或换模型都跑一遍，看通过率而不是看感觉。

**换模型必须重跑测试**。不同模型在结构化能力上差异明显，同一份契约换个模型可能表现完全不同。

**契约和提示词一起做版本管理**。契约变了，下游解析代码也要跟着变，把它们当作同一份资产存起来，出问题时才能回溯是哪次改动引入的。

**监控解析成功率**。把它当成一个线上指标，低于阈值就告警，而不是等下游报数据不对了才发现。

**能用确定性规则就别用大模型**。格式转换、字段映射、字符串切割这类事，用代码做比用模型做可靠得多。模型的价值在判断和归纳，不在搬运格式。

## 常见问题

### 模型已经有 JSON 模式了，还需要手写输出契约吗？

需要。JSON 模式能保证输出是合法 JSON，但保证不了字段齐全、类型正确、取值在枚举范围内。也就是说它解决的是语法层，业务上真正容易出问题的是结构层和语义层——字段时有时无、数字被写成字符串、枚举值被自由发挥。契约描述的是「你要什么数据」，模式约束的是「它用什么格式说」，两者分工不同，同时用才稳。

### 输出内容比较长时，总在快结束时被截断，怎么处理？

先做减法再谈加固。把一次长输出拆成多次短输出：先让它输出条数清单，再逐条或分批补全内容，每批只处理有限条数。同时把契约里最长的文本字段放到最后，因为它最容易被切掉。最后一招才是重试——但原样重跑大概率还是会在同一位置截断，必须配合拆分或缩短要求才有效。

### 让模型顺便解释一下推理过程，会影响结构化输出吗？

会，而且是常见的破坏源。要求它在数据前面先说思路，等于允许它在 JSON 之前自由输出，客套话和解释就一起回来了。如果确实需要理由或依据，正确做法是把它变成契约里的一个字段，比如单独设 evidence 或 reason 字段，让解释待在 JSON 内部，而不是飘在外面。

### 重试几次还是解析失败，接下来该做什么？

停止重试，走兜底。连续多次失败通常说明任务本身超出了单次输出能稳定承载的范围，继续重试只是在烧额度和时间。可行的兜底有三条：一是拆任务，把一个大输出拆成若干小输出分别处理；二是降目标，先只提取最关键的几个字段，剩下的留到下一轮或人工补齐；三是转人工，并把这次的原始输出存进纠错集，攒够样本后再回头改契约。
