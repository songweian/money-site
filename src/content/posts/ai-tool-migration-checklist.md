决定换 AI 工具往往只要十分钟：看到更合适的方案、团队统一了采购、或者旧工具某个功能不再够用。真正麻烦的是一两个月之后——某条每周自动汇总的流程悄悄不再更新，翻遍新平台也找不回当初调了半天的那版提示词，客户资料还留在旧账号里没人导出，而旧账号已经被注销了。

**AI 工具迁移不是「重新注册一个账号」，是带着资产搬家。** 会丢的东西分三层：显性数据（聊天记录、上传的文件）、隐性配置（提示词背后的设定、字段名、触发条件、密钥）、关系链（谁有权限、哪个机器人在调用、哪份文档里写着旧链接）。大部分人只搬了第一层，第二层和第三层是在失效之后才被发现的。

下面按实际迁移顺序给一套可复用的做法：先盘点，再备份，然后逐类搬，接着并行验收，最后收尾。整套流程对个人和十几人的小团队都适用，不需要额外的迁移工具。

## 先分清你要迁的是哪五类资产

动手之前先把「要搬的东西」列全。经验上，AI 工具里的资产可以归成五类，它们的可导出性和丢失风险差别很大。

| 资产类型 | 典型内容 | 最容易丢的东西 | 迁移前先做什么 | 难度 |
| --- | --- | --- | --- | --- |
| 提示词与模板 | 常用角色设定、输出格式、 few-shot 示例 | 没写进文本的模型和参数设定、迭代过的版本 | 补齐上下文说明，存成带版本号的纯文本 | 低（但最易低估） |
| 对话与生成记录 | 历史问答、草稿、客户沟通记录 | 时间戳、附件、引用来源、当时的模型 | 用结构化格式导出，别只留 PDF | 中 |
| 知识库与文件 | 上传的文档、切片后的索引、标签体系 | 原始文件、文件与引用的对应关系 | 保留一份未加工的原件，再单独建索引 | 中高 |
| 自动化流程与集成 | 定时任务、webhook、字段映射、失败告警 | 凭据、触发地址、下游系统的字段名 | 画一遍「触发—处理—落库—通知」链路 | 高 |
| 账号与权限设置 | 成员、共享链接、API 密钥、订阅 | 别人手里存的旧链接、待结算账单 | 列出所有协作者和外部调用方 | 低但影响面广 |

这张表的价值不在分类本身，而在于**逼你承认有些东西根本导不出来**。比如提示词里那句「按我们上周定的格式来」，在原平台靠上下文撑着，复制到新平台就成了一句没有依据的指令；再比如知识库重建后，同一份文档的分块方式变了，原来能命中的引用可能就找不到了。这些都得靠人补，不是导入向导能解决的。

盘点时给每项标注三件事：责任人、被谁依赖、最后一次使用时间。最后一栏特别有用——很多「感觉很重要」的流程其实已经三个月没跑过，可以直接放弃，不必花力气迁。

## 迁移前：三件必须先做的不可逆准备

**第一，把盘点结果落成一张所有人都能看到的表。** 不要只存在一个人的笔记里。表里至少写清旧位置、新位置、当前状态（未开始／已迁移／已验收）、以及验收人。迁移一旦跨人协作，靠记忆对齐必然出漏子。

**第二，备份「原始格式」，而不是加工后的结果。** 上传过的 PDF、表格、图片要留原件，聊天记录要留结构化导出，自动化流程要留配置导出或截图加文字说明。原因很简单：原文件可以重新切片、重新导入，而一份渲染好的摘要或截图不能。备份文件建议按「日期＋来源平台＋资产类型」命名，另存一份到团队共用的位置，不要只放本地磁盘。

**第三，设一个冻结窗口。** 在开始搬迁到验收完成之间，暂停往旧平台新增模板、新建流程、改字段。同时通知所有协作者和外部调用方：哪段时间会有双份数据、以哪一边为准。冻结不是形式主义，它能避免「旧平台还在改、新平台已经复制了一份」这种最难排查的分叉。

各平台的导出能力、历史记录保留范围、导出文件格式差别很大且经常调整，具体以各产品官网的最新说明为准，不要照搬任何一篇教程里写的具体限制。

## 提示词怎么迁：别只复制文本

提示词是看起来最容易、实际最容易「迁完就失效」的一类。同一段文字换个模型或换个产品，输出语气、字段完整性、对长上下文的处理都可能变，原因往往不在文字本身，而在于旧环境里那些没写出来的默认设定。

建议按三步做：

1. **补全上下文**。把原来依赖环境的信息显式写进模板：目标读者、输出格式、不允许做什么、示例输入输出、以及这版模板适用的任务范围。一句「按老规矩整理」在迁移后必须换成具体规则。
2. **存成可回归的资产**。每条模板带上版本号、修改人、适用场景和一组典型输入。这块可以直接沿用[提示词版本管理的做法](/posts/prompt-version-control-team/)，迁移期正好是补齐版本记录的契机。
3. **准备回归样本集**。挑十到二十条真实任务，记下旧平台的标准输出（不必逐字相同，但要有明确的验收点：必须出现哪些字段、不能出现什么、格式长什么样）。在新平台逐条跑一遍，对不上的先改模板，别急着改流程。

如果流程里用到 JSON 之类的机器可消费输出，迁移后要重新跑一次字段校验和必填项检查——**换了模型之后最危险的失败不是报错，而是字段还在、值悄悄变了**。这类约束写法和自动重试机制可以参考[结构化输出的实操说明](/posts/ai-structured-output-json/)。

## 对话记录、知识库与文件怎么迁

这一层的原则是：**结构化格式优先，原件单独留存，索引允许重建**。

对话记录尽量用平台提供的 JSON、CSV 或 Markdown 导出，PDF 只作为最终留档副本。PDF 会把「谁说的、什么时间、引用了哪个附件」压成一段连续文字，之后既不能检索也不能重新导入。导出后先做三个抽查：时间范围是否完整、附件是否在包里、含表格或代码的消息有没有变形。发现缺失要在旧账号还在的时候补导，越晚越被动。

知识库更建议**放弃「搬索引」、改为「重建索引」**。把原始文档按目录整理好，记录原有的分类与标签，在新平台重新上传、重新切片。这样虽然多花一点时间，但引用关系清晰可控；试图把旧平台的分块结果硬搬过去，往往因为切片策略不同而产生一堆查得到但读不通的片段。重建之后，用五到十个已知答案的问题做召回测试，确认关键内容能被找回来。

涉及客户名单、合同、未公开财务数据的资料，迁移期间要额外确认两件事：文件会不会经过第三方中转、新平台的权限范围是否与旧平台一致。共享链接通常是全量可访问的，重建后务必逐条重新设置可见范围，不要默认继承。数据保留期、文件是否用于训练、导出是否包含附件，均以官网最新说明为准。

## 自动化流程与集成最容易断的四个点

自动化是迁移里风险最高的一类，因为它平时不报错，断了也不一定有人立刻发现。搬之前先把每条流程画成一条链：触发 → 取数 → 处理 → 写入 → 通知，然后逐段核对下面四点。

- **触发器**。webhook 地址、定时任务表达式、轮询频率、监听的事件类型，换了平台基本都要重新配。特别注意那些「只在旧平台里存在」的触发器，比如某个应用的内置事件，新平台可能要用轮询或中间层替代。
- **凭据**。API 密钥、OAuth 授权、环境变量、服务账号权限。迁移时最容易发生的是「本地能跑、线上不能跑」——因为本地用的是个人账号，线上依赖的是即将被回收的旧授权。建议趁机把密钥统一收进配置管理，并给每个密钥标注所属流程。
- **字段映射与数据形状**。同样的字段名，两边可能一个传字符串、一个传数组；日期格式、空值表示、编码也常不一样。写库之前加一层显式转换和校验，比事后清洗便宜得多。
- **失败处理**。重试次数、超时、幂等键、告警发到哪里。新流程上线初期建议先只写测试表或加 dry-run 开关，确认无误再放开写入，避免重复执行产生脏数据。

从零搭建与稳定运行的基础做法可以看[无人值守自动化流水线指南](/posts/github-actions-automation-guide/)；如果是换编排工具（比如从托管方案换到自托管），还要把运行成本、运维责任一起算进去，取舍逻辑与[托管和自托管的对比](/posts/make-vs-n8n/)类似。

关键提醒：**不要在切换当天直接改生产流程**。先在测试环境双写，跑通几个完整周期，再按流程逐条切，每切一条立即验证下游是否正确收到。批量一次性替换，出问题时很难判断是哪一条链路断了。

## 并行运行期：怎么验收再切流量

新旧工具并行跑一段时间，是整套迁移里性价比最高的一步。只比较「哪个回答得更好」没有意义，要对照的是能不能稳定替代原来的工作。

建议同时记录四类指标：任务成功率（含失败和超时）、输出字段完整度、结果是否需要人工返工、单次任务耗时。成本另记一栏，但别急着用单价下结论——迁移期双跑本来就重复计费，且计费方式与免费额度以官网为准。量化口径可以直接复用[AI 提效效果评估](/posts/ai-productivity-measurement/)里的思路，先定义什么叫「一次成功」，再统计。

更重要的是**提前写死回滚条件**：连续出现多少次失败、关键字段缺失达到什么比例、或者某个下游系统报错，就立即切回旧流程。阈值按自己的业务定，白纸黑字写进迁移表里。真出事的时候，没有人有余裕现场开会讨论「要不要回滚」。

并行期结束的判定标准不是「时间到了」，而是：回归样本全部通过、真实任务连续若干周期无人工兜底、所有下游确认收到正确数据、以及可以明确说出旧流程何时关停。四条都满足再切。

## 切换后 30 天的收尾

切完不等于结束。按下面的顺序收尾，比一次性注销安全得多：

1. **旧账号先保留观察期**。不要立刻注销，也不要立刻清空数据。保留期间每周看一次是否还有请求打到旧环境。
2. **回收权限与撤销密钥**。移除不再需要的成员、作废旧 API 密钥、关闭旧的 OAuth 授权。这一步比取消订阅更紧急，因为泄露风险和账号是否还付费无关。
3. **更新所有引用点**：团队文档、浏览器书签、聊天机器人配置、对外共享链接、定时任务的回调地址。这类散落的引用通常比想象中多，可以用站点后台或日志里的来源反查一遍。
4. **处理订阅与账单**。确认结算周期、取消生效时间、注销后数据保留多久，全部以官网账单与帮助中心说明为准，不要凭印象推断。
5. **归档迁移记录**。把盘点表、备份位置、回归结果、回滚条件和最终决策留档。下次再换工具时，这份记录能省掉大半的重新盘点。

## 高频翻车点与避坑清单

- **只导出聊天记录就宣布迁移完成**：提示词、流程、权限三类资产没动，几周后集中爆发。
- **把 PDF 当中间格式**：结构丢失，无法回导、无法检索，只能人工重录。
- **提示词复制后不回归**：语气看着差不多，但 JSON 少了一个必填字段，下游静默写入空值。
- **忘了 webhook 和回调地址**：流程本身搬好了，上游还在往旧地址推数据。
- **权限默认继承**：新平台共享范围比旧平台宽，敏感文件意外暴露。
- **同一批任务双写且没有幂等**：并行期产生重复记录，清理成本高于迁移本身。
- **旧账号注销太快**：发现漏项时配置和日志已经一起没了，只能凭记忆重搭。
- **没有回滚条件**：出问题时靠临场判断，往往拖到影响扩大才决定切回。

## 一张可以直接抄的迁移验收清单

迁完逐项打勾，任何一项没过就先别关停旧流程：

- [ ] 五类资产全部盘点完毕，每项都有责任人和依赖方
- [ ] 原始格式备份已另存到团队共用位置，并完成一次可恢复性抽查
- [ ] 冻结窗口已通知到所有协作者与外部调用方
- [ ] 提示词模板已补全上下文、带版本号，回归样本全部通过
- [ ] 对话与文件以结构化格式导出，附件、时间戳、来源抽查无缺失
- [ ] 知识库索引已在新平台重建，关键问题召回测试通过
- [ ] 每条自动化链路的触发器、凭据、字段映射、失败处理已逐段核对
- [ ] 并行期四类指标已记录，回滚条件已写明并有人负责执行
- [ ] 下游系统确认收到正确数据，双写产生的重复记录已清理
- [ ] 权限、密钥、共享链接、机器人配置、文档书签全部更新
- [ ] 旧账号进入观察期，订阅与注销安排已确认
- [ ] 迁移记录归档完毕

把这张清单当成「旧流程关停许可」：只要还有空格，就说明搬家只搬了一半。迁移真正的完成标志不是新工具能用，而是**旧工具可以安全地被忘掉**。

## 常见问题

### 换 AI 工具时，最容易被漏掉的是哪类数据？

不是聊天记录，而是「隐性配置」：提示词里没写出来的模型与参数设定、自动化流程的触发条件、字段映射、密钥和告警去向、以及别人手里保存的共享链接。这些通常不在导出文件里，也不会出现在新平台的导入向导中。做法是在切换前用一张表逐个列出「谁在用、依赖什么、最后一次跑是什么时候」，把关系链先记下来，再动数据。只导出聊天记录就以为搬完了，是迁移里最常见也最难补救的失误。

### 能不能直接把旧平台的聊天记录导成 PDF 存档？

可以拿来留档，但不要把它当成迁移的中转格式。PDF 会丢掉结构：谁说的、什么时间、引用了哪个附件、当时的提示词版本，往往都压成一段文字，之后既没法检索也没法重新导入。优先用平台提供的 JSON、CSV 或 Markdown 等结构化导出，PDF 只作为最后的法律或审计留存副本。另外，导出功能是否开放、能导多久范围内的记录、附件是否包含在内，各家差别很大且经常调整，请以各产品官网的最新说明为准。

### 新旧工具要不要并行跑一段时间？

要，而且这一步不能省。建议在同一批真实任务上同时跑一段时间，对照四类结果：任务成功率、字段完整度、输出能不能直接用、以及每次任务耗的时间。只看「新工具回答得更好」就切过去，很容易漏掉结构化字段错位、附件丢失这类不会报错的问题。同时提前写死回滚条件，比如关键字段缺失超过某个比例就立刻切回旧流程；具体阈值按自己的业务定，别等出了问题再临时讨论。并行期也要留意两边的用量和账单，计费规则与免费额度以官网为准。

### 切换完成后旧账号能马上注销吗？

不建议。先保留一段观察期，确认没有遗漏的自动化任务、共享链接、协作者权限和待结算账单，再分层收尾：先回收成员权限和撤销密钥，再更新文档、书签、机器人和 webhook 地址，最后才处理订阅与账号注销。订阅的结算周期、取消后数据保留多久、注销是否可撤销，各家规则不同，请以官网账单与帮助中心说明为准。急着一刀切注销，最常见的后果是某个季度都没人用的定时任务突然失效，而配置和日志已经一起没了。
