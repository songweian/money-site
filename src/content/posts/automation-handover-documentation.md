去年冬天，一个朋友的公司在周五下午发现所有自动报价邮件都停了。

搭这套流程的运营三个月前离职，交接时说了句「n8n 里都配好了，看着改就行」。接手的人打开后台，二十多条工作流名字叫 `test-3`、`新流程副本`、`老王改过的`，节点里的表达式引用了三张没人知道的表格，还有一个 Webhook 指向一个已经停用的子域名。

真正让它停下来的不是逻辑错误，是某个 API Key 到期了。而那个 Key 注册在原作者的私人账号下，续期链接发到了他已经注销的邮箱。

这件事的教训不在于「文档很重要」——这句话谁都说过，说了也没用。真正的教训是：**交接的完成标准不是「文档交出去了」，而是「接手的人独立改动过一次，并且成功回滚过」。** 没经过这一步，文档只是一份没人验证过的猜测。

这篇文章讲怎么把自动化流程交出去：交接包里该放什么、凭据怎么移交才不出事、文档写到什么颗粒度、怎么做代跑验收，以及交接完成后怎么防止文档慢慢烂掉。

## 交接失败，通常不是文档没写，而是没人验证过

把失败形态分清楚，才知道该补哪一块。

**只写了「是什么」，没写「为什么」。** 文档里写「每 10 分钟拉一次订单」，但没写为什么是 10 分钟——因为上游接口有缓存，更频繁拉只会拿到重复数据。接手的人觉得 10 分钟太慢，改成 1 分钟，然后数据开始重复入库。

**凭据跟着人走。** 密钥、OAuth 授权、Webhook 签名、第三方平台的 API Token，只要有一个挂在个人账号下，这个人离开就等于流程的一半离开了。这类问题在交接清单里最容易被漏掉，因为它不在「流程」里，在「账号」里。

**没有运行证据。** 文档说「这个流程很稳定」，但没人知道它上次失败是什么时候、失败长什么样、告警发给了谁。接手的人第一次遇到失败时，没有任何参照物。

**下游没人知道。** 流程 A 的输出是流程 B 的输入，B 又给三个人发报表。交接只交了 A，改 A 的字段名时，B 静默失败了两周才被发现。

这四种失败有一个共同点：它们都不是「信息缺失」，而是「信息没被使用过」。所以交接的核心动作不是写，是演练。

## 交接包里必须有的六样东西

一份能用的交接包，最少包含这六块。缺任何一块，接手的人都会在某天卡住。

**一、资产清单。** 一条流程一行，写清：流程名称（人话，不是 `test-3`）、所在平台与工作区、流程 ID、触发方式与频率、归属账号、输出到哪里、下游有谁在消费。这份清单的价值在于，它是唯一一份「全公司有哪些自动化在跑」的视图——大多数团队其实没有这个东西。

**二、逻辑说明。** 触发 → 处理 → 输出三段，加上分支条件和边界情况。重点不是复述节点，而是标出「哪几步是有判断的」和「哪几步一旦失败会污染数据」。

**三、凭据与账号台账。** 不存明文密码，存四件事：这个凭据叫什么、存在哪（平台密钥库 / 环境变量 / 密码管理器）、谁有权取、什么时候到期。第四项最常被漏，也最容易致命。

**四、运行证据。** 最近十次左右的执行记录截图或导出、至少两个失败样本及其报错、告警配置截图、以及「过去半年出过什么事」的口头史。运行证据的作用是给接手的人一个基线——他需要知道「正常」长什么样。

**五、变更与事故记录。** 改过什么、为什么改、改完效果如何。不需要很正式，一个按时间倒序的列表就够，但它能解释掉文档里所有看起来莫名其妙的设定。

**六、代跑脚本。** 一份「照着做就能复现一次成功运行」的步骤清单，包括：在哪里点运行、用什么测试数据、跑完去哪里看结果、看到什么算成功。这一块是演练的基础，也是整份交接包里唯一必须被真正执行过的部分。

## 四种交接方式，覆盖面和代价差得很远

大多数团队的交接是「约个会讲一遍」，这种方式的信息留存率低得惊人。把几种方式放在一起对比，取舍会清楚很多。

| 交接方式 | 能覆盖什么 | 大致耗时 | 适合场景 | 主要缺陷 |
| --- | --- | --- | --- | --- |
| 口述带教 | 整体思路、踩过的坑、人情世故 | 1-2 小时 | 流程简单、接手人已在同一团队 | 无记录，两周后基本遗忘；无法异步查阅 |
| 录屏讲解 | 操作路径、界面位置 | 2-3 小时 | 界面操作复杂、步骤多 | 视频难检索；界面改版后立刻失效 |
| 文档 + 资产清单 | 结构、凭据位置、下游依赖 | 半天到一天 | 流程中等复杂、原作者仍在职 | 文档可能与实际不符，且无人验证 |
| 文档 + 代跑演练 | 上述全部，加上真实故障处理经验 | 一到两个工作日 | 涉及钱、客户或对外发布的关键流程 | 需要双方同时在场，排期成本高 |

表格里最值得注意的一行是最后一行。它的耗时看起来是前几种的两三倍，但它省掉的是「原作者离开后，全团队逆向猜两周」的成本。对关键流程来说，这笔账几乎总是划算的。

如果排期排不开，一个折中方案是：**关键流程走完整演练，非关键流程只做文档 + 资产清单 + 凭据台账**。但凭据台账不能省——它是唯一一项「不做就一定会出事」的内容。

## 凭据移交：交接里最容易出事的一块

流程逻辑写错了，最多跑错一次；凭据管错了，可能泄露一整年都没人发现。所以这一块值得单独处理。

**原则一：凭据归组织，不归个人。** 所有 API Key、OAuth 授权、Webhook 签名密钥，都应该挂在服务账号或组织级账号下，而不是某个员工的个人账号。个人账号下的凭据有三个隐藏成本：人走了要重建、审计时说不清、权限往往过大。

**原则二：最小权限，且能单独吊销。** 一个只读报表的流程，不应该拿着可写的全权限 Token。理想状态是「一条流程一个凭据」，出事时能精确吊销而不影响其他流程。各平台对密钥数量、作用域粒度和轮换周期的支持差异很大，具体以官网文档为准。

**原则三：有到期时间，且到期前有人知道。** 永久有效的密钥是最危险的，因为没人会记得它。设定 90 天或 180 天轮换，并把到期日写进台账、加进日历提醒。轮换本身应该是一条自动化流程——否则它一定会被跳过。

**原则四：交接时必须做一次「个人授权清查」。** 具体动作是：登录每个集成平台，查看授权列表里有没有离职或转岗同事的个人账号，有就撤销。这一步在很多平台上要手动点，无法完全自动化，所以要写进交接清单，作为签收项。

还有一个容易被忽略的点：**测试凭据和生产凭据要分开**。交接时如果只交了生产密钥，接手的人为了试错往往会直接在生产环境上改，风险成倍放大。

## 文档怎么写才真的有人看

文档没人看，通常不是因为写得少，是因为写得像说明书——只有「是什么」，没有判断依据。

一个反例和正例的对照：

> **反例：** 第 3 步：调用订单接口，取 `updated_at` 大于上次执行时间的记录，写入表格。

> **正例：** 第 3 步：增量拉取订单。用 `updated_at` 而不是 `created_at`，因为订单会被修改（改地址、改金额），只拉新建会漏掉变更。时间窗口往前多取 5 分钟做重叠，重复记录靠第 5 步的去重节点消化。**改这里要注意：** 如果下游报表按 `created_at` 统计，重叠窗口会导致重复计数，改之前先确认报表口径。

正例多出来的部分，全是接手的人真正需要的东西：为什么这么选、哪里留了冗余、动它会伤到谁。

三个写法上的建议：

**每个关键节点写三行。** 这段在干什么 / 为什么这么做 / 改它会影响谁。第三行最难写，也最值钱。

**边界条件单独成节。** 空值怎么处理、重复触发怎么办、接口超时重试几次、命中速率限制时是等待还是跳过。这些在正常运行时永远看不到，但接手的人第一次遇到故障时全靠它。

**标出「不要动」的地方。** 有些看起来多余的步骤其实是补丁，比如一个空节点、一次多余的等待、一个写死的常量。它们背后通常有一次事故。文档里明确写「此处不要优化，原因见事故记录」，能省掉一次重演。

## 四步代跑演练：让文档接受检验

演练是整份交接里唯一能把「文档」变成「能力」的环节。四步，每一步都由接手的人操作，原作者只在旁边看，不主动指点。

**第一步：原样复跑。** 用测试数据完整跑一次，不做任何修改。目的是验证文档里的路径是对的、凭据是可用的、输出是符合预期的。这一步失败很正常，失败的地方就是文档需要修的地方。

**第二步：受控改动。** 改一个不影响生产的参数，比如把一个筛选条件放宽、把发送对象改成测试群、把阈值调大一点。然后重新跑，观察结果变化是否符合预期。这一步检验的是「他是否真的理解了这条流程的因果」，而不只是会点按钮。

**第三步：故障注入。** 故意让一个环节失败：临时停用一个凭据、让某个接口返回 500、把输入数据改成空。观察三件事：流程是否按预期失败、告警是否发到了正确的人、失败后数据是否留下脏状态。这一步最有价值，因为它把「半年后才会遇到的事」提前到了今天。

**第四步：回滚。** 把第二步的改动撤回，把第三步制造的脏数据清理掉，确认流程回到初始状态。回滚做不干净，说明这条流程本身缺乏可逆性，这是设计问题，要记进文档并排期修。

每一步都要留记录：做了什么、看到什么、和预期差在哪。这份记录本身就是交接包的最后一块拼图，也是下一个人接手时的运行证据。

关于流程本身怎么写测试用例、怎么设计断言，可以配合[自动化流程测试的实操方法](/posts/automation-workflow-testing/)一起看；演练偏「人能不能接手」，测试偏「流程对不对」，两者互补。

## 接手前的验收清单

把上面所有内容压成一张可以打勾的表，交接双方一起过一遍，全部打勾才算交完。

- [ ] 资产清单完整，流程名是人话，能一一对应到平台里的实际流程
- [ ] 每条流程标明了触发方式、频率、归属账号、下游消费方
- [ ] 逻辑说明覆盖了所有有判断的分支，边界条件单独成节
- [ ] 凭据台账记录了「叫什么、存在哪、谁能取、何时到期」四项
- [ ] 没有凭据挂在个人账号下，或已有明确的替换排期
- [ ] 测试凭据与生产凭据已分开，接手人有独立的测试入口
- [ ] 最近十次运行记录可查，至少两个失败样本已交底
- [ ] 告警指向岗位或群，而不是某个人的私聊
- [ ] 变更与事故记录可读，能解释文档里所有「看起来多余」的设定
- [ ] 接手人独立完成过一次原样复跑
- [ ] 接手人独立完成过一次受控改动，并说清了影响面
- [ ] 故障注入验证过：会失败、会告警、不留脏数据
- [ ] 回滚验证过，且回滚步骤已写进文档
- [ ] 个人授权清查已完成，离职同事的授权已撤销

清单里打不了勾的项，不要用「大概没问题」放过。交接这件事的特点是小漏洞的代价极不对称——省下的两小时，可能换来某个周末的紧急排查。

## 交接之后：让文档不腐化的三个机制

交接不是一次性事件。文档写完那天就开始过期，真正决定它能不能长期有用的，是后面三个机制。

**变更即更新。** 改流程必须同时改文档，两者在同一个提交里审。这条规则听起来很硬，但只要允许「下次再补」，就再也不会补了。如果流程本身在代码仓库里（比如 GitHub Actions 的 workflow 文件），可以顺手让 CI 检查配置改动是否伴随文档改动。

**季度轮值代跑。** 每季度安排一个不是原作者的人，按文档跑一遍演练的前两步。这既是文档的回归测试，也是团队的能力备份。轮值的人不必是固定角色，反而越随机越好——随机才能暴露文档里那些「只有某个人看得懂」的表述。

**告警指向岗位，不指向个人。** 告警发给个人，那个人休假时就等于没有告警。改成发到值班群或工单系统，并明确「谁在什么时限内响应」。这一条改起来只要五分钟，但它是流程能否在人员变动中存活的分水岭。

顺带一提，如果你的自动化里包含需要人确认的环节，交接时要把「谁有权批准、批准不了的兜底路径」一并交出去，否则接手人会在第一次需要审批时卡住。这部分的设计思路可以参考[自动化触发方式的选择](/posts/automation-trigger-selection/)里关于人工审批触发的那一节。

## 常见问题

### 交接文档要写多细，难道要写到每一步点哪里吗？

不需要写到点击级别，那类文档一定会在界面改版后失效。要写到「决策级别」：这一步在做什么、为什么用这个方式做、改它会连带影响哪些地方、什么情况下它会失败。具体到字段映射、阈值取值、接口地址这类内容，建议直接写在流程节点的备注里或配置文件的注释里，让文档只承担「为什么」和「谁负责」，把「是什么」交给系统自己呈现。判断标准很简单：接手的人拿着文档，能不能在不问原作者的前提下判断「这个改动会不会炸」。

### 原搭建的人已经离职，账号和密钥都拿不回来怎么办？

按「止损优先」的顺序处理。第一步先把现存流程完整导出或截图存档，确认还能跑；第二步盘点哪些凭据是绑在个人账号下的，逐个在平台侧新建服务账号或组织级密钥替换掉，替换时保留新旧并行一段时间，确认新凭据可用再停用旧的；第三步联系平台管理员走账号回收流程，把原作者的个人授权从所有集成里移除。如果某个凭据彻底拿不回来，就把它当成「已泄露」处理，直接吊销重建，不要抱着侥幸继续用。具体的账号回收与密钥轮换流程各家平台不同，以官网文档为准。

### 手上一堆没文档的老流程，是先补文档还是先重写？

先分级，再决定。把流程按「跑错一次损失多大」和「多久跑一次」两个维度分成四格：损失大且高频的，必须优先补文档并做代跑演练；损失小且低频的，可以只留一页说明加告警联系人；损失大但极低频的，考虑直接下线或改成人工触发；损失小且高频的，反倒最值得重写——因为高频意味着维护成本会持续累积。不要一上来就全部重写，那通常的结果是重写到一半，旧流程还在跑，新流程没人敢切。

### 交接要花这么多工夫，小团队真的值得吗？

取决于这条流程离开原作者还能不能活。如果流程只服务一个人、坏了也没人受影响，那不写文档是理性的；但只要它对接了客户、财务数据或对外发布，就必须至少有「资产清单 + 凭据台账 + 代跑记录」这三样。真正昂贵的不是写文档的两小时，而是原作者休假或离职那天，全团队停下来逆向猜一条没人看得懂的流程。把交接当成流程上线的一部分，而不是离职时才想起的补课，成本会低很多。

把交接做扎实，还有一个副作用值得说：写文档的过程会逼着你重新看一遍自己搭的东西，很多之前「能跑就行」的设计，会在解释给别人听的时候暴露出来。这也是为什么最好的交接时间点不是离职前一周，而是流程刚稳定下来的那一周。
