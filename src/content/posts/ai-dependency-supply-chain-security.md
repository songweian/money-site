你让 AI 加一个「把日期格式化成相对时间」的功能，它顺手写了 `import from 'time-ago-format'`，还贴心地补了一句「这个库很轻量」。你把代码粘进项目，`npm install` 一路绿灯，构建也过了。

问题在于，这个包可能根本不存在。而它不存在这件事，本身就是一个可以被利用的缺口。

这是 AI 编程普及之后新出现的一类风险：**模型的输出成了依赖清单的上游来源**。以前项目的依赖是人挑的、评审过的，现在有一半是模型顺手写出来的。这条链路一旦没人管，供应链安全的所有前提都失效了。

本文不讨论宏观的软件供应链理论，只讲一件事：当你的代码里有相当比例是 AI 写的时候，依赖该按什么流程管。

## 为什么 AI 写出来的依赖特别容易出问题

大模型生成 import 语句的方式，和它生成其他代码的方式是一样的——基于概率补全，而不是基于「这个包真的存在于 registry 里」的事实核查。

它见过海量的开源代码，知道在这个位置通常会出现一个什么样的标识符：命名风格对、缩写习惯对、生态惯例也对。于是它会写出一个「看起来完全合理」的包名。这个包名可能来自几个真实包的拼接，可能是某个流行库的旧称，也可能纯粹是命名规律的产物。

这就带来三个后果：

- **模型不知道自己错了**。它给出的是一段语法正确、风格一致的代码，没有「我不确定这个包存不存在」这样的信号。你在对话里追问，它往往会继续编造版本号和 API 文档。
- **错误会自我强化**。同一个提示词多跑几次，如果几次都吐出同一个不存在的包名，你会误以为这是社区共识。
- **错误会沉淀**。代码提交、CI 通过、上线运行，只要那个位置恰好没有被执行到，这个问题可以潜伏几个月。

而攻击者对这个缺口非常熟悉。既然模型会稳定地编造某些包名，那么把这些名字抢先注册下来，就是在等模型把用户送上门——这类手法业内称为「slopsquatting」，可以理解为「等着 AI 送流量」的抢注。它比传统的错拼抢注更省事，因为不需要猜用户会打错哪个字，只需要猜模型会编出哪个名字。

## 三类故障，后果完全不同

同样叫「依赖出问题」，实际差别很大，处理方式也不一样。

**第一类：包不存在。** 安装直接失败。这是最好的一种，因为它在最早的时刻暴露了自己。真正麻烦的是它发生在本地能跑、CI 装不上、或者反过来——某个私有 registry 里恰好有个同名包，于是悄悄装上了别的东西。

**第二类：包存在但不是你以为的那个。** 名字对，作者不对；或者名字对，但版本号是模型编的，实际不存在，安装器于是回退到某个老版本，API 签名不一样，运行时才炸。这类问题的排查成本最高，因为报错信息指向的是业务代码，不是依赖本身。

**第三类：包存在、作者也是真的，但版本或来源被换掉了。** 这是纯粹的攻击场景：投毒的传递依赖、被接管的维护者账号、被篡改的镜像源。它和 AI 没有直接因果关系，但 AI 加速了依赖数量的增长，也就放大了这类风险的暴露面。

三类故障对应三套不同的防线，把它们混在一起谈「加强依赖管理」是没有意义的。下面按可执行顺序展开。

## 三种治理手段各管什么

先厘清工具边界。很多团队上了 lockfile 就以为安全了，这是最常见的误解。

| 手段 | 解决什么问题 | 拦不住什么 | 落地成本 |
| --- | --- | --- | --- |
| 锁文件（lockfile） | 保证每次安装得到完全相同的版本树，环境可复现 | 拦不住首次引入的错误包，也不判断包是否可信 | 极低，装完就有，只需提交进仓库 |
| 来源限制（registry 白名单 / 私有镜像） | 保证只从受信任的源取包，挡住同名冒名与镜像投毒 | 拦不住白名单源里本身就有的恶意包 | 中，需要配置 registry 与鉴权 |
| 依赖审计（漏洞库比对 + 新增包人工确认） | 发现已知漏洞，拦住来源不明的首次引入 | 拦不住零日漏洞，也挡不住逻辑后门 | 中，CI 里加一步 + 团队约定 |

关键结论：**锁文件管一致性，来源限制管渠道，审计管可信度**。三者是串联关系，缺任何一环，另外两环的价值都会被打折。

## 第一步：把 AI 提议的依赖当成外部输入

这是流程上最容易被跳过、但收益最大的一步。

心理上的转变很简单：模型给出的包名，和你从陌生邮件里复制来的命令，属于同一信任等级。你不会因为一封邮件写得专业就执行它附带的脚本，那么也不该因为一段代码写得漂亮就无条件安装它的依赖。

具体做法：

- 在团队规范里明确写一句「AI 生成代码中的新增依赖，必须由人确认后加入清单」。这句话不需要工具支撑，但需要写下来，否则没人会执行。
- 在 code review 时把「依赖清单有没有变化」当成一个独立检查项，而不是顺带看一眼。参见 [AI 代码评审的流程分工](/posts/ai-code-review-workflow/)，依赖变更应该单独走一个标签。
- 让提出者说明理由：这个包解决什么问题、有没有用现有依赖实现的办法、维护状况如何。如果答案是「AI 说这个好用」，那就退回重写。

这一步的成本几乎为零，能挡掉的却是比例最高的一类问题。

## 第二步：锁死来源与版本

如果第一步靠人，这一步靠配置，目的只有一个：让安装行为变得可预测。

**统一入口。** 在项目根的 `.npmrc`、`pip.conf` 或 `go env` 里显式指定 registry，只允许公司镜像或官方源。这样即便有人误装了一个同名包，也会因为源里没有而失败，而不是从某个未知源成功装上。私有镜像的存储与流量配额各家不同，具体额度以官网为准。

**清单与锁文件必须同源。** 清单里写范围、锁文件里写确定版本，两者不一致时以锁文件为准安装、以清单为准审计，冲突就报错。CI 里跑一次 `npm ci`（或等价的严格安装命令）而不是 `npm install`，前者会在不一致时直接失败，后者会悄悄帮你「修好」。

**区分直接依赖与传递依赖。** 直接依赖是你能审的，传递依赖你审不过来，所以要限制它们的来源：开启 lockfile 的完整性校验、禁止从 git 地址或 tarball URL 直接安装、对需要执行安装脚本的包单独设白名单。很多生态允许配置「忽略安装脚本」的策略，这条对拦截恶意 postinstall 特别有效——代价是少数需要编译的包会装不上，那就把它们单独列出来放行。

## 第三步：装之前先核验存在性

这一步是纯技术动作，几秒钟一个包，应该固化成习惯。

各生态都有只查元数据、不执行代码的命令，用它来判断包是否真实存在、维护是否正常：

- Node：`npm view <包名>` 看版本、发布时间、维护者、仓库地址
- Python：`pip index versions <包名>`，或在隔离环境里 `pip download --no-deps`
- Go：`go list -m -versions <模块路径>`

看到下面这些信号，就该停下来多问一句：

| 信号 | 为什么可疑 |
| --- | --- |
| 只有一两个版本，全部集中在最近几周 | 新注册、无使用历史，名字又刚好「很合理」 |
| 包名与某个流行库只差一两个字符或一个连字符 | 典型的仿冒命名 |
| 没有仓库链接，或链接指向一个空仓库 | 无法追溯源码 |
| 周下载量极低但 README 写得极其完整 | 内容像是批量生成的，目的是让你放心 |
| 有 postinstall / setup.py 里的网络请求 | 安装即执行，是最常见的落地方式 |
| 维护者账号是新注册的，同时持有多个相似包 | 批量抢注的典型特征 |

这些信号单独出现都不构成结论，两三条叠加时基本可以判定不该用。此时正确的做法不是「装上看能不能跑」，而是让 AI 换一种实现——多数情况下，你要的功能用标准库或已有依赖写十行代码就够了。

## 第四步：在 CI 里加一道供应链闸门

人工检查会疲劳，配置会过期，所以最终要落到自动化上。这条闸门不需要多复杂，四件事就够：

1. **严格安装**：用锁定模式安装，清单与锁文件不一致即失败。
2. **漏洞扫描**：`npm audit --audit-level=high`、`pip-audit`、`govulncheck` 之类，按严重级别设阈值。注意漏洞库有滞后，扫描通过不等于安全，它只是底线。
3. **来源校验**：解析锁文件里的所有 resolved 地址，任何不在白名单 registry 内的条目直接报错。这一步能挡住「本地能装、CI 装的是另一个东西」的诡异情况。
4. **依赖变更需显式批准**：把依赖清单文件的变更设为需要指定人 review 的路径，或者用 CODEOWNERS 机制限定审批人。

这四步可以复用你已有的 [CI 流水线](/posts/github-actions-automation-guide/)，不需要额外平台。要注意的是扫描本身会拖慢构建，如果流水线已经偏慢，参考 [CI 构建提速的排查方法](/posts/ci-build-speed-troubleshooting/) 把它做成并行 job 或只在依赖变更时触发。

## 第五步：出事之后的止损顺序

假设最坏的情况发生了：某个包已经装进了开发机和构建机，安装脚本也跑过了。这时候顺序比动作更重要。

**先断，后查。** 立刻从清单和锁文件移除该包，重新安装，确认它从依赖目录里消失；同时把构建缓存里对应的条目清掉，否则下次构建会把它从缓存里恢复回来。

**然后轮换凭据。** 这是最容易被忽略、后果最严重的一步。安装脚本能读到的东西包括：环境变量里的所有令牌、`~/.aws` 和 `~/.ssh` 下的文件、CI 的 secret、数据库连接串、以及任何明文写在配置里的密码。这些全部按已泄露处理，逐个更换。CI secret 更换后还要检查最近的部署记录，确认没有异常的发布。

**再取证。** 翻安装日志的时间点、检查该包有没有安装钩子、看机器上有没有新增的定时任务或未知进程、核对云账单有没有异常调用。这一步的目的是判断影响范围，而不是追责。

**最后补流程。** 复盘时要问的不是「谁装错了」，而是「为什么这个包能进到清单里而没人拦」。答案通常指向前面四步中缺失的那一环。整体止损思路和 [自动化流程回滚](/posts/automation-rollback-idempotency/) 是相通的：先恢复可用状态，再处理根因。

## 新增依赖前的自查清单

把这份清单贴在 PR 模板里，逐条勾选，比任何安全培训都管用。

1. 这个包的真实用途能用一句话说清，且不能用现有依赖替代？
2. 包名拼写与官方文档一致，不是从 AI 输出里直接复制的？
3. 已用元数据命令确认包存在，且最新版本发布时间不是「几天前」？
4. 仓库地址可访问，源码与包名、README 描述一致？
5. 维护者不是新注册账号，且没有同时持有多个高度相似的包？
6. 有安装脚本的，脚本内容已读过，没有对外网络请求和文件读取？
7. 依赖来源在白名单 registry 内，锁文件里的 resolved 地址也指向同一处？
8. 版本范围写得足够窄，没有用 `*` 或过宽的 caret 范围？
9. CI 的严格安装与来源校验都通过，漏洞扫描无高危项？
10. PR 里写明了引入理由，且由了解这块的人 review 过？

十条里如果有任何一条答不上来，就不要合并。这不是流程洁癖——依赖一旦进了主干，清理成本远高于此刻多问一句。

顺带一提，这套思路和 [防提示词注入](/posts/prompt-injection-defense-checklist/) 是同构的：核心都不是「让模型别犯错」，而是**假定上游产出不可信，把校验放在下游**。模型会继续编包名，这一点不会因为换更强的模型而消失；能改变的只有我们这一侧的流程。

## 常见问题

### AI 写出来的 import 语句，我肉眼看着挺像真的，怎么快速判断包是否存在？

不要靠肉眼，靠命令。Node 生态用 `npm view 包名` 或 `npm info 包名 version`，Python 用 `pip index versions 包名`（或在隔离环境里 `pip download --no-deps` 试拉一次），Go 用 `go list -m -versions` 模块路径。这些命令只查元数据、不执行任何代码，几秒钟就能给出结论。更省事的做法是把它写进编辑器的保存钩子或 pre-commit：只要 diff 里新增了 import 或依赖声明，就自动跑一次存在性核验，查不到的直接拦下来。关键是别在主力环境里先装再看——一旦装上了，安装脚本已经跑过了，核验就失去意义。

### 项目里已经有 lockfile 了，是不是就不需要担心这类问题？

lockfile 解决的是「装到的版本和上次一样」，解决不了「这个包本身是坏的」。如果某次提交把一个幻觉包名连同它生成的 lockfile 一起提交上去，之后每次安装都会稳定地装上那个包，锁文件反而把风险固化了。lockfile 的正确定位是可复现性的基础，它必须配合另外两件事才有安全意义：一是新包的引入要经过人工确认，二是 CI 里要校验 lockfile 与清单文件一致、且所有来源都在允许的 registry 里。换句话说，锁文件管一致性，审计管可信度，两者不能互相替代。

### 团队小、没有安全岗，供应链防护做到什么程度算够？

按投入产出排序，先做三件成本最低的事：所有新增依赖必须走一次人工确认（哪怕只是在 PR 里留一句「为什么加它」），CI 里加上依赖漏洞扫描和来源白名单，生产环境的凭据不放在开发者本地。这三件事基本不需要额外工具预算，却能挡掉绝大多数「AI 顺手加了个包」引发的事故。SBOM 生成、构建产物签名、私有镜像仓库这些属于第二阶段，等团队有专职运维或者开始对外交付时再补。不必一开始就追求完整体系，先把「谁能往项目里加依赖」这个口子收紧。

### 如果已经发现装上了可疑的包，第一件事该做什么？

先断而不是先查。第一步把该包的版本从清单和 lockfile 里摘掉，重新安装并确认它从 `node_modules` 或 `site-packages` 里消失；第二步立刻轮换这台机器和生产环境上所有可能被读到的凭据——环境变量里的令牌、云厂商密钥、数据库密码、CI 的 secret，因为安装脚本最常见的目的就是把这些东西读走。第三步才是取证：翻安装日志、看该包有没有 postinstall 之类的钩子、核对最近有没有异常的网络请求或账单波动。顺序不能反，先花半天做取证，等于给攻击者多留半天使用已泄露凭据的时间。
