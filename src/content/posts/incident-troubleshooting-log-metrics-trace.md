线上出故障最难受的不是问题本身，而是**不知道该看哪里**。监控面板一片红，日志在滚，群里在问"是不是挂了"，你却要在几分钟内回答三个问题：影响多大、从什么时候开始、大概是哪一环。

绝大多数团队的排查之所以慢，不是因为缺工具。日志平台、指标面板、链路追踪，该有的都有，但因为三类信号没有分工，出事时所有人一起翻日志，靠关键词和人肉经验碰运气。

本文不讲怎么搭平台，讲**排查顺序**：出故障后先动哪一样、再动哪一样，以及为了让这个顺序能跑通，平时该把日志打成什么样、告警怎么设才不吵。

## 出故障的前五分钟：先确认影响面，再找原因

新手最常见的动作是立刻去翻日志找报错。这往往是错的——错误日志里的异常可能一直存在，和这次故障毫无关系，你会被带偏。

正确的第一步是**用指标确认影响面**，回答三个问题：

- **影响的是谁**：全部用户，还是某个渠道、某个地区、某个版本？
- **影响的是什么**：完全不可用，还是变慢，还是某个功能失效？
- **从什么时候开始**：是缓慢劣化，还是某个时间点突然断崖？

这三个问题的答案决定了后面的排查方向，也决定了要不要立刻回滚。如果是某个时间点突然断崖，**第一反应应该是"刚刚上线了什么"**，而不是查代码——部署、配置变更、证书过期、第三方接口调整，这几样占突然性故障的大多数。

影响面还有个现实作用：**它决定了你对外怎么说。** 在还没定位到原因时，"部分用户在提交订单时失败，从 14:20 开始，我们正在处理"已经是一句合格的同步，比沉默或含糊其辞强得多。

## 指标：告诉你"坏了"，但说不出"哪里坏"

指标是聚合后的数字：请求量、错误率、响应时间、队列长度、CPU 和内存。它的优势是**快且便宜**，一眼能看出趋势和拐点，适合做告警和容量判断。

它的短板同样明显：**指标是聚合的，天然丢掉了个体信息。** 你知道错误率从 0.5% 涨到 12%，但不知道这 12% 的请求有什么共同点——是某个用户的、某个参数的、还是某个下游超时引起的。指标能精确到"某一分钟开始变坏"，但没法告诉你"是谁的请求在坏"。

所以指标的正确用法是**用来定位时间窗和范围，而不是用来找原因**。把错误率曲线和响应时间曲线叠在一起看，还能快速区分两类故障：

- 错误率涨、耗时没变 → 通常是逻辑问题或依赖返回了错误，比如参数校验变严、下游接口改了返回结构。
- 耗时涨、错误率随之涨 → 通常是容量或依赖问题，比如慢查询、线程池打满、下游超时引发连锁失败。

这个区分能省下大量时间，因为它直接把排查方向砍成两半。

## 日志：回答"发生了什么"，前提是字段打得对

日志是唯一能还原单个请求全过程的东西。但它的有效性完全取决于**你当初打了什么**。

很多团队的日志长这样：`处理失败` 或 `user error`。这种日志在排障时约等于没有——它既不能告诉你哪个请求，也不能告诉你为什么。一条能用的日志至少要有这几类字段：

| 字段类别 | 具体字段 | 排障时的作用 |
| --- | --- | --- |
| 身份 | 请求 ID、用户 ID（或设备 ID）、会话 ID | 把同一次请求在所有服务里的日志串起来 |
| 位置 | 服务名、实例标识、代码位置或处理阶段 | 判断是全局问题还是单实例问题 |
| 时间 | 时间戳（含时区）、耗时毫秒数 | 跨服务对齐时间线，找出慢在哪一步 |
| 结果 | 状态码、错误类型、错误码 | 区分是客户端问题、服务端问题还是依赖问题 |
| 上下文 | 关键入参（脱敏后）、重试次数、依赖方标识 | 判断是不是某类参数或某个下游触发的 |

其中**请求 ID 是整套体系的地基**。没有它，跨服务的日志只能靠时间戳猜对齐，服务一多就完全不可靠。做法很简单：在入口生成一次，放进日志上下文和响应头，调用下游时透传，所有日志自动带上。这一步的投入极小，但没有它，后面买什么平台都救不了。

另外两条经验：**日志要结构化输出**（JSON 而非拼接字符串），否则查询只能靠正则，字段一多就没法聚合统计；**错误日志要带上下文而不是只带错误信息**，把关键入参和依赖返回值一起打出来，否则你还得再复现一次才能拿到现场。

敏感信息另说：手机号、身份证、令牌这类字段要么不打，要么在日志组件层面统一脱敏，不要靠每个开发自觉。

## 链路追踪：回答"卡在哪一环"

当一次请求要穿过网关、应用、缓存、队列、数据库和若干外部接口时，光看日志会陷入一个困境：每个服务都说自己没问题，拼起来却就是慢。

链路追踪解决的就是这个：它把一次请求在所有组件里的每一段耗时串成一棵树，你能直接看到 800 毫秒里有 620 毫秒花在一次数据库查询上。

它的价值**随服务数量增长而放大**。两三个服务的单体应用，日志带上请求 ID 基本够用；服务一多、调用链一深，靠人肉对齐日志几乎不可能，这时链路追踪从"锦上添花"变成"必要条件"。

需要注意的是，链路追踪有采样问题。全量采集的开销和存储成本都不低，多数团队会按比例采样（具体比例和成本请结合自己使用的平台官网说明评估）。采样一定要**按请求一致性采样**——同一个请求要么整条链路都采，要么都不采，否则会出现半截链路，比没有更误导人。

## 三类信号怎么配合：一次完整的定位过程

把三者串起来，一次典型的排查是这样的：

1. **告警触发**（指标）：订单接口错误率 5 分钟内从 0.3% 升到 9%。
2. **看曲线**（指标）：耗时同步上涨，判断是依赖或容量问题，不是逻辑问题。
3. **确认范围**（指标）：按渠道拆分，只有移动端受影响；按时间看，从 14:20 开始。
4. **查变更**：14:15 有过一次配置发布——重点嫌疑对象。
5. **翻日志**：按时间窗和移动端条件筛出失败请求，发现错误集中在调用支付网关超时。
6. **看链路**：挑几个失败请求看链路，确认耗时全在支付网关这一段，且重试了三次。
7. **定位与止损**：支付网关地址在新配置里写错，导致连接超时后重试放大。回滚配置。
8. **补防线**：给这条外部调用加单独的成功率告警和超时预算，配置发布前加连通性校验。

整个过程里，**指标负责缩小范围，日志负责拿到现场，链路负责确认环节**。三类信号不是三套重复建设，而是三个不同粒度的切片。只有指标，你知道坏了不知道为什么；只有日志，你知道为什么但不知道影响多大；只有链路，你知道卡在哪但不知道是不是普遍现象。

## 日志字段与采样：一份能直接照做的清单

如果只能做一件事让未来的排查变快，做这份清单：

- **入口生成请求 ID**，透传给所有下游调用，写入响应头。
- **日志改为结构化输出**，统一字段名和取值枚举，别让每个服务各写各的。
- **错误必须带上下文**：关键入参（脱敏）、依赖方、重试次数、原始错误。
- **分层采样**：错误与关键业务事件全量保留，普通访问日志按比例采样，调试日志默认关闭、按需临时开启。
- **设置保留期**：热数据保留短周期供排障，冷数据归档长周期供审计与趋势分析，具体容量与费用以所用平台的官网说明为准。
- **统一时间**：所有服务用 UTC 打时间戳，展示层再转本地时区，避免跨时区排查时对不上。
- **在日志里暴露依赖标识**：调用哪个第三方、用了哪个实例，出问题时能直接问对方。

这份清单不需要买任何商业平台，自建也能做八成。真正难的不是技术，是**团队约定后能不能一直执行**——建议把字段规范写进代码模板或日志组件里，让开发默认就打对，而不是靠文档和自觉。

## 告警降噪：让报警值得把人叫醒

排查体系再好，如果告警本身是噪声，一切白搭。告警被忽视通常有两个原因：

**一是阈值太敏感。** CPU 偶尔冲到 80% 就发消息，一天几十条，人自然就屏蔽了。改法是加持续时长条件（连续 N 分钟超阈值才告警），并配恢复通知，避免"告警来了又自己好了"没人确认。

**二是告警没有对应动作。** 这是更常见的根因：一个指标超了，但没人知道接到之后该干什么。判断标准很简单——**如果一个指标异常后不需要任何人做任何事，它就不应该是告警，而应该是仪表盘上的一条曲线。**

分级也值得做：按用户可感知程度分，只有真正影响用户的才值得打断人（电话、强提醒），其余进工单或日报。这样值班的人才会相信"响了的都是真事"。

最后留一条底线：**保留一条不做任何优化的"裸"检查**，比如每分钟一次的端到端拨测，模拟真实用户走一遍核心流程。聚合指标可能全绿而用户实际已经用不了，拨测是唯一能抓到这类问题的东西。

## 常见问题

### 小团队没有专职运维，指标、日志、链路应该先上哪个？

先上指标和结构化日志，链路追踪可以缓一步。原因是前两者的投入产出比最高：指标让你知道系统是否活着、慢到什么程度，日志让你知道具体哪条请求失败、失败原因是什么，这两样就能覆盖绝大多数单体应用和小规模服务的排查场景。链路追踪的价值随服务数量增长而放大，只有两三个服务时，在日志里带上请求 ID 基本够用。建议的顺序是：先给入口接口配好成功率和耗时指标，再把日志改成带请求 ID 的结构化输出，等服务拆到五个以上、跨服务调用开始频繁时再引入链路追踪。

### 日志全量打会不会很贵，采样比例应该从多少开始？

成本取决于日志量和保留时长，不同云厂商与日志服务的计费方式、免费额度和单价都不一样，具体请以各自官网的最新说明为准。实践中不需要一开始就全量无差别保留，可以按用途分层：错误日志和关键业务事件全量保留，普通访问日志按 10% 到 20% 采样，调试日志默认关闭、排障时临时开启。采样要注意两点：一是必须基于请求 ID 做一致性采样，即同一个请求要么全采要么全不采，否则排障时日志会断成一截一截；二是采样不能绕过错误，凡是标记为错误的请求必须全量落地，否则恰恰是你最需要的那些日志被丢掉了。

### 链路追踪是不是只有微服务架构才需要？

不是只有微服务才需要，但确实服务的调用层级越多收益越大。单体应用里，一次慢请求的原因可能是数据库慢查询、外部接口超时或某个同步循环，如果在关键函数入口加一层轻量埋点，同样能看出耗时分布在哪里，不必引入完整框架。真正的分水岭是「是否跨进程」：一旦一次用户请求要穿过网关、应用、缓存、队列和数据库，靠单个服务的日志拼凑时间线会非常痛苦，这时链路追踪的收益就明显超过成本。判断标准很简单：如果排查一次问题需要打开三份以上的日志才能对齐时间线，就该考虑了。

### 告警多到已经麻木了，除了直接删告警还能怎么办？

先分清两类问题：一类是阈值定得不合理，抖动就触发；另一类是告警本身没有可执行的动作，响了也没人知道该干什么。前者改成持续时长触发，比如连续五分钟超过阈值才告警，并要求一个明确的恢复通知，避免告警来了又悄悄好了没人确认。后者更常见也更该处理：每条告警都应该对应一个明确的处置动作，如果一个指标超了但没人需要做任何事，它应该是仪表盘上的一条曲线而不是一条告警。另外建议按用户可感知程度分级，只有影响到真实用户的才值得打断人，其余的进工单或日报。删除告警是最后手段，且不要删了就不管，要记录为什么删。
