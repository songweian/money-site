很多人把 AI 用得不顺，第一反应是"这个模型不行"，但换一个模型之后问题依旧。真正的原因往往在提示词：**你给出的信息不足以让模型判断你想要什么。**

提示词工程不是背咒语，而是把"你脑子里默认的上下文"显式写出来。这篇文章讲一套能沉淀、能复用、能交给团队的方法。

## 高质量提示词的五个要素

把下面五项补齐，输出质量会有肉眼可见的提升：

| 要素 | 作用 | 缺失时的典型症状 |
| --- | --- | --- |
| 任务 | 明确要做什么 | 模型答非所问，输出一堆无关内容 |
| 背景 | 说明场景与对象 | 语气、专业度不匹配 |
| 约束 | 划清边界与禁区 | 编造数据、跑题、过度发挥 |
| 输出格式 | 规定结构 | 每次格式都不一样，无法程序化处理 |
| 示例 | 给出参照样本 | 风格不稳定，需要反复人工修 |

其中**输出格式**最容易被忽略，但它是从"手动复制粘贴"走向"程序化处理"的分水岭。要求返回 JSON、Markdown 表格或固定字段，才能让 AI 的输出接进你的工作流。

## 一个可直接复制的通用模板

```
# 任务
{一句话说明你要它做什么}

# 背景
- 面向读者：{谁会看这段输出}
- 使用场景：{输出会被用在什么地方}
- 已有材料：{粘贴或简述上下文}

# 约束
- 必须：{必须包含的内容}
- 禁止：{绝对不能出现的内容}
- 字数/长度：{范围}
- 事实要求：{不确定时的处理方式}

# 输出格式
{给出明确结构，例如：先给结论，再给 3 条理由，最后给行动建议}

# 示例
{一个你认可的样例，哪怕只有两三行}
```

使用时不必每次都填满，但**任务、约束、输出格式这三项建议永远保留**。

## 三个高频场景的具体写法

### 场景一：把长内容压缩成决策摘要

关键是规定"结论优先"和"必须保留的数字"：

> 你是我的分析助手。请把下面的材料压缩成一份决策摘要。要求：第一句话直接给结论；随后列出 3 条支撑理由，每条不超过 30 字；原文中出现的所有数字、时间、金额必须原样保留；无法从材料推出结论时写"材料不足"，不要推测。输出为 Markdown，包含"结论""理由""风险"三个二级标题。

### 场景二：让输出可被程序消费

结构化输出要写死字段，并明确异常处理：

> 分析下面的用户反馈，返回严格 JSON，不要输出任何 JSON 之外的内容。字段：sentiment（positive/neutral/negative）、topics（字符串数组，最多 3 个）、summary（不超过 50 字）、needs_followup（布尔值）。如果反馈内容为空或无法判断，sentiment 返回 neutral，needs_followup 返回 true。

### 场景三：改写与风格迁移

风格类任务给示例比给形容词有效十倍：

> 请把下面的文案改写成面向技术决策者的风格：多用短句，去掉感叹词和营销形容词，每个结论后面跟一个具体的技术细节或数据。参考下面这段示例的语气：{粘贴一段你认可的文字}。保持原意不变，长度控制在原文的 80%-120%。

## 一套可量化的调优流程

靠感觉调提示词，容易陷入无止境的微调。用一个固定测试集来推进：

1. **准备 5-10 个真实任务**，覆盖你的高频场景，作为测试集。
2. **写第一版提示词**，跑完所有任务，标注哪些达标。
3. **一次只改一处**（通常是补约束或补示例），再跑一遍测试集。
4. **记录变化**：把每次改动和达标率写进表格。
5. **达标率稳定后固化成模板**，交给团队复用。

**核心原则是"一次只改一个变量"。** 同时改三处，你就永远不知道是哪一处起了作用，也就不可能沉淀出可复用的经验。

## 常见误区

- **过度堆砌形容词**：「非常专业的、极其详细的、完美的」这类词几乎不起作用，换成可验证的要求（例如"至少给出 3 个具体案例"）。
- **把重要要求埋在长段落中间**：把关键约束放在开头或结尾，并用分条列出，模型对列表形式的约束遵循度更高。
- **不给退路**：一定要写"不知道就说不知道"。没有这句，模型在缺信息时会倾向于编造。
- **忽略负面示例**：除了给"要什么"，再给一句"不要什么"，效果往往立竿见影。

## 把提示词变成团队资产

个人层面的提示词价值有限，真正放大收益的是沉淀成库：

- 按**场景**而非按工具组织（工具会换，场景不变）。
- 每条模板记录**适用场景、失败案例、最后更新时间**。
- 用变量占位（`{读者}`、`{材料}`），让同事拿到就能填。
- 每季度做一次回归测试，淘汰失效的写法。

**判断提示词库是否有效的标准很简单：新同事第一天上班，能不能靠它直接产出合格结果。** 如果还要手把手教，说明模板里的背景和示例还不够具体。

## 常见问题

### 提示词要写得非常长才算好吗？

不需要。关键是信息是否充分。五个要素齐全的短提示词，通常远胜于堆满形容词的长提示词。如果输出不达标，优先补"约束"和"示例"，而不是加长度。

### 模型经常不遵守输出格式怎么办？

三招：把格式要求放在提示词最后（靠近输出位置）；给出一个完整的格式示例；需要程序消费时明确写"只返回 JSON，不要任何解释文字"。必要时在代码里做一次容错解析。

### 中文任务需要注意什么？

明确写出语言要求和语境。例如"面向中国大陆读者，使用简体中文，避免直译的英语句式"，比单纯说"用中文回答"效果好得多。

### 有必要购买提示词课程或合集吗？

大部分付费内容的价值可以通过自己做测试集获得。建议先自己跑十次对比实验，建立起判断力，再决定是否需要外部资料。
