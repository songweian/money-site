凌晨两点，一条每周自动同步的流程把同一批客户邮件发了两遍。第二天早上你打开后台，看到的是三百多条重复记录、几十封客户回复，以及一个还在继续跑的定时任务。

这种时刻最容易被两种冲动带走：一是立刻打开编辑器改配置，二是直接删掉流程了事。两种做法都会让事情更难收拾——前者毁掉现场，后者让「到底哪些数据被动过」永远查不清。

**自动化出事之后，正确的顺序是：先让动作停下来，再算清影响面，然后才谈修。** 修复是最后一步，不是第一步。下面这套流程适用于 n8n、Make、GitHub Actions，也适用于你自己写的脚本，区别只在操作按钮的位置。

## 先分清三种「跑错」，处置动作完全不同

「跑错了」是一句很笼统的话。实际排查时，先把它归类，后面的动作会清晰很多。三种类型的影响面和处置优先级差别极大：

| 类型 | 典型表现 | 影响面特征 | 第一优先动作 | 能否自动补 |
| --- | --- | --- | --- | --- |
| 重复执行 | 同一批记录写了两遍、邮件发了两封、工单重复创建 | 数据污染，越晚处理越多 | 立刻停调度，防止第三遍 | 能，靠去重与合并 |
| 漏跑 / 静默失败 | 该发的日报没发、该同步的订单没进来，但没人报错 | 数据缺失，往往几天后才发现 | 先补数据，再补监控 | 能，靠批次对账 |
| 逻辑写错 | 字段映射错位、筛选条件反了、金额算错 | 结果看起来正常，其实是错的 | 先停，再判断能否按批次回滚 | 部分能，取决于是否留了旧值 |

三类里最危险的不是第一种，是第三种。重复执行会立刻被人发现，逻辑写错却常常安静地跑上几周——数据一直在写，报表一直在出，只是全都不对。这类问题唯一可靠的发现方式不是等它报错，而是定期拿结果和上游原始数据对账。

## 第一步：止损，三步，几分钟内完成

止损的目标不是「修好」，是「让损失停止扩大」。三步按顺序做：

**第一，暂停调度，不要删除流程。** 删除会连同运行历史一起丢掉，而运行历史是后面算影响面唯一的依据。大多数平台都支持临时停用或禁用触发器，n8n 里可以停用工作流，Make 里可以关闭 scenario，GitHub Actions 里可以直接禁用 workflow。停用是可逆的，删除不是。

**第二，断开所有对外产生动作的节点。** 停掉触发器只是不再有新的一轮，正在跑的这一轮还会继续往下走。发信、写库、调用支付、创建工单、发消息到群里——这些节点要单独断开或改成只记录不执行。一个实用做法是提前在每个对外节点前面放一个「开关」判断（读一个配置项或环境变量），出事时只改这一处，不用逐个节点改连线。

**第三，保留现场。** 把这一轮的输入数据、中间结果、输出结果、错误堆栈、执行时间戳原样导出，存到一个不会被执行流程覆盖的地方。很多平台的运行日志有保留期限，免费版往往更短，具体天数各产品不同，请以官网说明为准。需要留档的，趁现在导出。

这三步做完再去开编辑器。顺序颠倒的代价是：你改好了配置，却再也说不清哪些数据是被旧配置污染的。

## 第二步：算影响面，四个问题定生死

接下来要回答一个问题：这次出事，需要回滚，还是补偿？

先用四个问题把影响面框出来：

1. **动了哪些记录？** 精确到表名、字段、行数、时间范围。有批次 ID 的直接按批次查，没有的只能用时间窗口加条件筛，误差会大很多。
2. **有没有对外可见？** 邮件、短信、站内通知、客户能看到的状态变更。只要出了公司边界，回滚就不再是技术问题。
3. **下游有没有已经消费？** 数据被同步到了数据仓库、被报表读走、被另一个流程接着处理过，那这些下游也要一起处理，只改源头等于没改。
4. **数据能不能恢复？** 有没有写入前的备份、快照、变更日志？有没有保留旧值字段？这一条决定后面是可回滚还是只能认。

四个问题答完，走哪条路基本就定了：

| | 回滚 | 补偿 |
| --- | --- | --- |
| 适用场景 | 数据还在自己系统内，未对外，有旧值或备份 | 已对外发生，或旧值已被覆盖无法复原 |
| 典型动作 | 按批次撤回、恢复到快照、切回上一版流程 | 发更正说明、冲正记录、退款、人工逐一修正 |
| 风险 | 回滚本身也可能出错，需要先在副本上演练 | 无法完全消除影响，只能降低 |
| 判断依据 | 「能不能让状态回到跑之前」 | 「回不到之前，怎么让现状可接受」 |

现实里最常见的错误判断是：把补偿当回滚。删掉数据库里的记录，就当事情没发生过——但客户手机上的邮件删不掉。所以第 2、3 个问题的答案只要有一个是「是」，就必须按补偿来设计。

## 回滚要分三层做，别只盯着数据库

很多人说的回滚只是「把数据改回去」，实际上要回滚的东西有三层，漏掉任何一层都会留下隐患。

**第一层，流程版本。** 出事之后通常要退回上一版配置。前提是你有版本。理想状态是流程定义本身存在 Git 里（n8n 的工作流可以导出成 JSON，Make 的 scenario 也有导出功能），每次改动都留一个可读的提交说明。退一步，至少要在每次大改前手动导出一份带日期的备份文件。没有版本历史的话，「退回上一版」只能凭记忆重搭，而记忆在凌晨两点是不可靠的。

**第二层，数据。** 三种做法，按可靠性排序：

- **按批次撤回**：每条写入带一个批次 ID（如 `run-20261105-0200`），撤回时按批次整体标记删除或改状态。可靠、可审计、可重复执行。
- **恢复到快照**：从写入前的备份或数据库快照恢复。彻底，但会连带的正常变更一起回退，通常只适合独立的表。
- **逐条修正**：没有批次也没有快照时的兜底，靠人工对照日志一条条改。最慢也最容易出错，只在影响行数很少时使用。

**第三层，外部副作用。** 已经发出的邮件、已经推送的消息、已经调用的第三方接口。这一层基本不可回滚，只能补偿：发更正邮件、在群里说明、把第三方系统里的记录改成撤销状态、走退款流程。处理这一层的关键是把「已发生」和「可撤销」分成两列写清楚，逐项划掉，别凭印象觉得「应该没发出去多少」。

顺带一句：回滚动作本身也要有幂等性。如果回滚脚本跑了两遍就把数据改乱了，那等于在同一次事故里摔两次。

## 幂等：让跑两遍等于跑一遍

事故处理完，真正要做的是让同类问题不再复发。核心手段只有一个：**让同一条流程重复执行任意多次，结果和只执行一次相同。**

实现上通常靠三样东西配合：

**一个稳定的幂等键。** 由业务属性拼出来，不能用随机 ID 或时间戳。比如「订单号 + 事件类型」「客户 ID + 账单月份」「文档 ID + 内容哈希」。键要满足两个条件：同一件事重复触发时键相同，不同的事键不同。

**一张去重表（或唯一索引）。** 每次执行前先查这个键在不在，在就跳过或更新，不在才继续。数据库层面加唯一约束更省心，因为并发情况下「先查再写」存在竞态窗口，唯一索引能兜住。没有数据库的场景，可以用平台的静态数据存储、缓存或一张专门的去重表代替。

**写入用 upsert，不用纯 insert。** 「存在就更新，不存在就插入」的语义天然幂等；纯 insert 在重试时必然产生重复行。

三个平台的做法差异不小，大致可以对上：

- **n8n**：可以在流程开头加一个查询去重表的节点，命中就走 no-op 分支；写入节点选支持 upsert 的数据库操作。执行记录的保留策略和并发设置会影响重试行为，具体选项以官网文档为准。
- **Make**：模块本身有部分去重和数据存储能力，也可以在流程前置一个过滤器。注意自动重试的开关和次数设置，默认行为不一定符合你的业务。
- **GitHub Actions**：靠 `concurrency` 组避免同一任务并行跑，用提交 SHA 或 issue 号做幂等键；工作流重跑是常态，所以任何写外部系统的步骤都必须自己保证幂等。

有一点容易被忽略：**幂等键要覆盖「整条链路」，不只是最后一个写入点。** 流程里如果先创建工单、再发邮件、最后更新 CRM，那么这三个动作各自都需要能识别「这一步已经做过了」。只给最终写入加去重，前面的中间步骤照样会重复。

## 重试不是越多越好，得先分清哪类错误值得重试

自动重试是把双刃剑。不加区分的重试会把一次小故障放大成一次数据事故——尤其在没做幂等的时候。

按错误性质分三类处理：

**值得重试的**：网络超时、连接被重置、第三方接口返回 429 限流、5xx。这类错误通常是暂时的，间隔一段时间再试大概率能成功。做法是指数退避（间隔逐次翻倍）加随机抖动，避免所有任务在同一秒集体重试把对方打挂。

**不该重试的**：400 参数错误、401/403 权限问题、422 校验失败、必填字段缺失。重试一百次结果都一样，只会浪费配额并掩盖真正的问题。这类错误应该直接失败并告警，让人来看。

**要谨慎的**：超时。超时最麻烦的地方在于你无法判断对方到底处理了没有——可能没收到，也可能处理完了只是回包丢了。所以超时重试必须配合幂等键，否则一次超时就等于一次重复写入。

另外两个参数要设死：**最大重试次数**（常见 3 到 5 次，再多通常说明问题不在临时性）和**最终失败的去向**（进死信队列、发告警、写失败表，绝不能静默丢弃）。流程里最危险的状态不是「报错」，是「失败了但没人知道」。

## 留痕与心跳，让「漏跑」也能被发现

重复执行会自己暴露，漏跑不会。一条每天该跑的流程连续三天没跑，界面上一切正常，只有靠人想起「好像没收到日报」才能发现。所以要专门为「没发生」设计监控。

两个低成本手段：

**批次留痕。** 每次运行写一条记录：批次 ID、开始时间、结束时间、处理行数、成功与失败计数、版本号。这张表既能用来做上面的回滚，也能用来做对账——今天处理了 0 行，和「今天没跑」是两种完全不同的故障，但表面症状一样，只有留痕才能区分。

**心跳。** 约定这条流程至少每 N 小时要写一次心跳，超时没有心跳就告警。这比「等它报错」可靠得多，因为进程被杀、调度器失效、凭据过期这几种情况都不会产生错误日志。

再补一条对账：每天拿下游表的总行数与上游应有的增量比一次，差值超过阈值就告警。这一步能抓到逻辑写错这类「看起来正常」的问题，是上面所有手段里唯一能覆盖它的。日志、指标、链路这三个层次的排查顺序，可以对照[线上故障排查的分层清单](/posts/incident-troubleshooting-log-metrics-trace/)来做，先看指标异常再看日志细节，别一上来就翻日志。

如果你还在搭流程的阶段，可以先看一下[用 n8n 搭第一条自动化](/posts/n8n-first-workflow/)里的失败告警部分，把告警通道先打通；跑在 GitHub 上的定时任务，可以参考[GitHub Actions 自动化流水线](/posts/github-actions-automation-guide/)里的稳定运行做法。这两篇讲的是怎么让它跑起来，本篇讲的是跑坏了怎么收场，配套看比较完整。

## 复盘只问五个问题，别写成检讨书

事故处理完之后要复盘，但复盘很容易变成两种无效产出：一份充满形容词的检讨，或者一堆「以后要加强」的口号。有效复盘只需要回答五个具体问题：

1. **这次的影响范围精确是多少？** 行数、人数、金额、时间窗。答不出来说明留痕不够，这本身就是一条改进项。
2. **第一个发现它的人或机制是谁？** 如果是客户投诉先发现的，那监控就是缺的；如果是告警先发现的，记下来是哪个告警起了作用，别以后把它关掉。
3. **从发生到止损用了多久？** 这个数字比「为什么会错」更值得优化，因为它决定了损失上限。
4. **哪一个设计缺陷让这次错误变成了事故？** 通常是缺幂等、缺批次 ID、缺旧值备份、重试没边界，四者之一。改这一处，比改十处细节有用。
5. **下次同类事故，处置时间能缩短到多少？** 把这次的止损步骤写成清单，下次照着做。预案的价值不在文档本身，在于它被真的用过一次。

## 上线前对照这 12 项

把上面的内容压成一份可以贴在下一次的检查表。不必全做，但每一项没做，都要知道自己在承担什么：

1. 每条写入记录都带批次 ID
2. 覆盖更新前保留旧值字段或快照
3. 对外动作（发信、支付、工单）挂在统一开关后面
4. 流程定义有版本，存在 Git 或定期导出
5. 关键写入点用 upsert，有唯一约束兜底
6. 幂等键由业务属性构成，不依赖时间戳
7. 重试只对超时、429、5xx 生效
8. 最大重试次数和最终失败去向已设定
9. 失败会发告警到有人看的地方
10. 有每日心跳，超时即告警
11. 每天与上游数据对账一次
12. 止损步骤写成了清单，任何人都能照做

十二项里，前六项决定「出事之后能不能收场」，后六项决定「出事之后多快能知道」。两边都做，自动化才敢真的无人值守。

## 常见问题

### 自动化流程跑错了，第一件事应该做什么？

先止损，再排查。顺序是：暂停调度但不要删除流程、断开所有会对外产生动作的节点（发信、写库、调用支付或工单接口）、把这一轮的入参、出参和运行日志原样留存。很多人第一反应是打开编辑器改配置，结果改完再想复现，现场已经没了。停掉动作、留住现场这两件事通常只要几分钟，却决定了后面能不能准确算出影响面。

### 数据写错了能直接回滚吗？

要看数据是怎么写进去的。如果流程走的是新增插入且每条记录带批次 ID，可以按批次整体标记删除或撤回到备份表，风险很低；如果是覆盖更新，旧值已经被冲掉，就必须依赖写入前的快照或数据库的变更记录，没有这两样基本无法复原。所以「能不能回滚」不是出事后决定的，而是在设计写入方式时就决定了。建议所有自动化写入都带批次 ID 并保留旧值，成本很低。

### 已经发出去的邮件、已经创建的工单怎么回滚？

外部副作用基本不可回滚，只能补偿。邮件发出去无法收回，能做的是立刻发更正或说明、把受影响名单拉出来单独跟进；工单和 CRM 记录一般可以改成已撤销状态并加备注；调用过支付或扣款接口的，要走退款流程而不是删记录。关键动作是把「已发生」和「可撤销」分开列清楚，别把删数据库记录当成事情结束了。

### 幂等和重试是一回事吗？

不是。重试解决的是「这次没成功，再试一次」，幂等解决的是「重复执行也不会产生重复结果」。两者必须一起用：只做重试不做幂等，一次超时重试就可能变成两条订单、两封邮件；只做幂等不做重试，遇到网络抖动就只能人工补跑。实现上通常是一个稳定的幂等键（比如业务单号加日期）配合一张去重表或唯一索引，写入用 upsert 而不是纯 insert。
