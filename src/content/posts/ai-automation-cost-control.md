很多团队把大模型接进自动化流水线之后，会经历同一个过程：第一周跑得很开心，第二周账单出来了，比预估高出一大截，但没人说得清多出来的钱花在哪。

问题通常不在单价。真正把费用推高的是三个放大器：**自动重试把一次失败变成多次计费、长上下文让单次调用的 token 数翻了几倍、无人值守的循环任务在你睡觉时持续消耗。** 这三件事叠加起来，调用量可以在你毫无察觉的情况下涨出一个数量级。

本文讲的是怎么把这件事管起来：上线前怎么估，上线后怎么设防，发现贵了之后从哪些地方动手。

## 先算清楚一次任务到底花多少钱

成本控制的第一步不是砍价，是能算账。很多流水线从上线到超支都没人算过单次调用成本，只有账单总额这一个数字，自然无从优化。

**把 token 拆成输入和输出两部分。** 大多数模型的计费是输入和输出分开算的，单价通常不在一个量级。而自动化场景里，这两部分的比例往往出人意料：你可能精心设计了一段很长的系统提示词和 few-shot 示例，输入侧几千 token，输出只要几十个字的分类结果。这种情况下，成本大头在输入，优化方向就该是压缩提示词，而不是限制输出长度。

**估算的实操方法。** 先取十到二十条真实输入，用模型的分词工具或者接口返回的用量字段，统计出输入 token 的中位数和 P90，别用平均值——长尾输入才是把账单推高的主力。输出的估算同理，但要注意推理类模型的输出可能包含大量中间过程，实际消耗远高于最终可见的文字量。拿到两个数之后，套用你所用模型的官网定价算出单次成本，再乘以日调用次数。**具体单价以各家官网公布的价格为准，且会随时间和模型版本调整，不要沿用几个月前记下的数字。**

**别忘了乘上失败系数。** 一条日均一千次调用的流水线，如果重试策略是失败后重跑两次、且失败率在百分之十左右，实际调用量会明显高出名义值。把失败率和重试次数一起算进估算，这个数字往往是最容易被漏掉的一块。

算完这一步你会得到一个基线：**每日成本 = 单次成本 × 调用次数 × (1 + 失败率 × 重试次数)**。之后所有的降本动作，都可以拿这个公式对号入座——降单价、降调用次数、降失败率，三选一或者组合。

## 三种接入方式的成本取舍

选哪种方式接入，决定了成本结构的基本盘。下面是三种常见方式的对比。

| 方式 | 成本结构 | 适合场景 | 主要风险 |
| --- | --- | --- | --- |
| 按量调用云端 API | 纯变动成本，用多少付多少，无最低消费 | 调用量波动大、早期验证阶段、峰值高均值低 | 单价随用量线性上涨，缺乏上限感，易被循环放大 |
| 云端批量 / 缓存通道 | 变动成本，但单价通常低于实时通道 | 可容忍延迟的离线批处理、输入高度重复的任务 | 有延迟，不适合交互式；缓存命中率低时无收益 |
| 自建或私有化部署 | 固定成本为主，机器费用占大头 | 调用量稳定且大、数据不能出网、有硬性延迟要求 | 低负载时单价极高；需要自己承担运维与升级成本 |

这张表的关键不是挑"最便宜"的，而是判断**你的负载曲线落在哪一段**。批量和缓存通道几乎是纯收益，前提是你的任务能容忍延迟；自建的分界线在于调用量是否稳定——一天只用几分钟的场景自建，等于为闲置的机器付费。

## 把成本关进笼子：限额、配额、告警三层防线

估算做得再准，也需要运行时兜底。防线要分三层，每层的目标和动作都不一样。

**第一层：单次调用的硬上限。** 直接限制单次请求的最大输出 token 数，以及在单个工作流里限制模型被调用的次数。这一层防的是死循环和失控的自动重试——一条本该调一次的任务因为条件判断写错调了五十次，靠账单发现就已经晚了。这一层的阈值应该保守，宁可偶尔误伤，也要挡住失控。

**第二层：按天或按周的预算阈值。** 给每个工作流、每个环境分别设一个预算，接近阈值时先告警，达到阈值时降级而不是直接停掉。降级的常见做法有三种：切换到更便宜的模型、把实时处理改为批量异步、或者排队等下一个周期。这一层是日常最常触发的一层，动作要温和。

**第三层：账户级硬限额。** 在服务商后台设置消费上限，作为最后一道兜底。这一层的作用是防"上面两层都没挡住"的极端情况，代价是触发即中断业务，所以数值要明显高于前两层。

**告警必须带上下文。** 一条"今日消费超标"的通知是没用的，收到的人不知道该查什么。有效的告警至少要带上：哪个工作流、哪个环节、调用次数相比昨日的变化、失败率是否异常。有了这些，接告警的人才能在几分钟内判断是流量涨了还是代码出 bug 了。

## 六个能立刻动手的降本杠杆

防线建好之后，再谈优化。下面六个手段按"先做什么"排序，越靠前越通用。

**一、模型分层。** 把流水线里的每一步按难度分类，简单环节用便宜的小模型，只在真正需要推理的环节用强模型。分类、抽取、格式转换、简单改写这类任务，小模型通常够用；多步推理、长文综合、严格遵循复杂约束的任务，降级容易翻车。**不要整条链路一起换**，逐环节测试后逐个切换，并保留随时切回的开关。

**二、压缩输入上下文。** 这是长提示词场景收益最高的一招。检查你的提示词里有没有这几样东西：几个月前加的、现在已经用不上的示例；为了"让模型更懂"而塞进去的大段背景文档；每次都原样重复的系统说明。更有效的做法是把稳定的长文档放到服务商提供的缓存机制里（如有），只把变化的部分放在每次请求中。**各家的缓存机制、生效条件和折扣比例不同，以官网说明为准。**

**三、约束输出长度。** 明确告诉模型你要多长的结果，并在接口层面设置最大输出 token 数。对推理类模型要特别注意，它的中间过程可能计入消耗，如果任务不需要展示推理链，就关掉相关选项。

**四、失败熔断与重试退避。** 与其失败后立刻重试三次，不如先判断失败类型：限流类错误适合退避重试，参数错误重试一百次也是错，内容不合规应该直接转人工而不是重试。给每类错误配不同的处理策略，能显著减少无效调用。

**五、批量与异步。** 对不要求实时返回结果的任务，走批量通道通常能拿到更低的单价。把白天零散触发的任务攒成夜间批次，是成本敏感场景的常见做法，代价是延迟。

**六、结果缓存。** 对输入高度重复的场景，把模型和输入做哈希建缓存。上线前先统计一周的输入相似度，命中率低于三成就别做了。要检查缓存键里是否混入了时间戳、订单号这类每次都变的字段，那会让命中率归零。

## 最小可用的成本看板

不需要建复杂的系统，先盯住四个数就够：**每日调用次数、每日消耗、平均单次输入 token、失败率。**

这四个数里最有诊断价值的是第三个。调用次数涨了可能是业务增长，也可能是死循环；消耗涨了可能是模型换了，也可能只是输入变长了；而平均输入 token 突然跳升，几乎总是提示词或上游数据出了问题。把这四个数按工作流拆分展示，异常一眼可见。

看板的意义不在于好看，而在于**让成本变化能追到具体的改动**。每次成本出现台阶式变化，都应该能对应到某次发布、某个提示词修改、或者某个上游数据源的变化。做不到这一点，优化就只能靠猜。

## 一周内把成本管起来的落地顺序

如果现在什么都没有，按这个顺序做，不要跳步：

**第一天**，给所有调用加上日志，记录工作流名、环节、输入输出 token、是否命中缓存、成功与否。没有数据，后面全是空谈。**第二天**，用真实数据算出单次成本和日成本基线，把公式写进文档。**第三天**，设置三层限额，从最保守的单次上限开始。**第四天**，配好带上下文的告警，确保有人会在收到后真的去看。**第五天**，搭四个数的最小看板，按工作流拆分。**第六和第七天**，才轮到优化——按前文六个杠杆的顺序逐个试，每改一个记一次数据对比。

**顺序不能反。** 先优化再建监控是最常见的错误：改完之后不知道有没有效，也不知道有没有引入新问题，最后只能凭感觉决定留不留。

## 常见问题

### 自己部署开源模型一定比调 API 便宜吗？

不一定，要看负载是否稳定。自建模型的成本主体是固定的机器费用，一天跑八小时和跑二十四小时花的钱差不多，只有持续高负载才能把单价摊薄。如果任务集中在每天几分钟、峰值很高但平均值很低，按量付费的 API 反而更划算。真正适合自建的是调用量稳定且量大、数据不能出内网、或者对延迟有硬要求的场景。**判断前先拿一周真实调用量算一遍，别凭直觉决策。**

### 限额应该设在什么位置才不会误伤业务？

分层设置，别只设一道总闸。最底层按单个工作流设单次调用上限，中间层按天设预算阈值，最上层才是账户级硬限额。三层的数值要有明显梯度，并预留熔断后的降级路径。只设一道总闸的后果往往是夜里被熔断，第二天早上才发现业务停了一整晚。

### 做了缓存之后，为什么成本没降多少？

通常是命中率不够，或者缓存键设计得太严。先统计一周的输入相似度，命中率低于三成说明这个场景不适合做缓存。另外要检查缓存键是否包含了时间戳、订单号这类每次都变的字段——把它们剥离出去，命中率往往能上一个台阶。

### 怎么判断该换更小更便宜的模型？

按任务拆开判断，不要整条流水线一起换。把每一步单独跑一遍测试集，看小模型能不能达到可接受的质量阈值。给每个环节标注"可降级 / 不可降级"，只对可降级的环节切换，并保留随时切回的开关。

## 小结

AI 自动化的成本问题，本质上不是"模型太贵"，而是**调用量在无人监管的情况下被放大了**。先能算账，再设防线，最后才动手优化——这个顺序反过来，就只能在账单出来之后亡羊补牢。

**所有价格、配额、折扣与缓存规则都以各家服务商官网当前公布的信息为准，本文给出的判断方法而非具体数字。**
